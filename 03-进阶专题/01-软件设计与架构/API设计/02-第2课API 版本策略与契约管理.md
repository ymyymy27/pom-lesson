# 第2课：API 版本策略与契约管理

## 1. 为什么需要版本？

```
v1 客户端期望：{ "name": "Alice" }
v2 服务端改成：{ "full_name": "Alice" }

无版本 → 旧客户端崩溃
有版本 → v1 继续返回 name，v2 返回 full_name
```

**API 是契约，变更必须可控。**

---

## 2. 版本策略对比

| 策略 | 示例 | 优点 | 缺点 |
|------|------|------|------|
| URL Path | `/v1/tasks` | 直观、易路由 | URL 污染 |
| Header | `Accept: application/vnd.taskflow.v1+json` | URL 干净 | 不直观、缓存复杂 |
| Query | `/tasks?version=1` | 简单 | 易被忽略 |
| 无版本 + 兼容 | 只加字段不删 | 零成本 | 难坚持 |

### 推荐

```
对外公开 API：URL Path 版本 /v1/ /v2/
内部微服务：可省略或用 Header
原则：同一 major 版本内向后兼容
```

---

## 3. 向后兼容规则

### 安全变更（不需要新版本）

```
✅ 添加新的可选字段
✅ 添加新的 endpoint
✅ 添加新的 enum 值（客户端应忽略未知值）
✅ 添加新的 query 参数（可选）
✅ 扩展错误码列表
```

### Breaking Change（必须新版本）

```
❌ 删除或重命名字段
❌ 改变字段类型（string → int）
❌ 改变 URL 结构
❌ 改变认证方式
❌ 改变错误码语义
❌ 将可选字段改为必填
❌ 删除 enum 值
```

---

## 4. 演进策略

### 扩展字段

```json
// v1
{ "name": "Alice" }

// v1 扩展（兼容）
{ "name": "Alice", "avatar_url": "https://..." }
// 旧客户端忽略 avatar_url
```

### 字段重命名（过渡方案）

```json
// 过渡期：两个字段同时存在
{
  "name": "Alice",        // deprecated，文档标注
  "full_name": "Alice"    // 新字段
}

// v2：只保留 full_name
```

### Sunset Header

```http
HTTP/1.1 200 OK
Sunset: Sat, 01 Jan 2028 00:00:00 GMT
Deprecation: true
Link: </v2/tasks>; rel="successor-version"

{
  "data": { ... }
}
```

## 5. 契约测试（Contract Testing）

```
问题：服务 A 调用服务 B，B 改了响应格式 → A 静默失败

解决：契约测试

Consumer（A）定义期望：
  GET /users/{id} → { id, name, email }

Provider（B）验证：
  实际响应匹配契约

工具：Pact、Spring Cloud Contract
```

### 流程

```
1. Consumer 写契约（期望的请求/响应）
2. CI 中 Provider 验证契约
3. 不兼容变更 → CI 失败 → 必须升 major 版本
```

---

## 6. API 生命周期管理

```
Design  →  Review  →  Implement  →  Document  →  Deprecate  →  Retire
   │          │            │              │             │            │
 OpenAPI    团队评审     代码+测试      发布文档      Sunset      关闭 endpoint
```

### 弃用流程

```
1. 文档标注 @deprecated + 替代方案
2. 响应加 Deprecation / Sunset header
3. 监控 deprecated endpoint 调用量
4. 通知集成方，给迁移窗口（通常 6-12 月）
5. 调用量归零后关闭
6. 记录 ADR
```

---

## 7. GraphQL vs REST 版本

```
REST：显式 /v1/ /v2/，版本清晰
GraphQL：通常无版本，通过添加字段 + @deprecated 演进

GraphQL 规则：
  ✅ 添加新 field
  ✅ @deprecated 旧 field
  ❌ 删除/改类型（Breaking）
```

## 8. TaskFlow 版本演进案例

### v1.0 初始

```
POST /v1/projects/{id}/tasks
{ "title": "...", "assignee_id": "..." }
```

### v1.1 扩展（兼容）

```
添加可选字段 priority, due_date
添加 GET /v1/tasks?filter[status]=done
```

### v2.0 Breaking

```
变更：
  - assignee_id → assignee: { id, name }（嵌入对象）
  - status enum 增加 "archived"，移除 "cancelled"
  - 分页从 offset 改为 cursor

迁移：
  /v1/ 继续维护 12 个月
  文档 + SDK 升级指南
  监控 v1 流量，逐步归零
```

## 9. API 设计评审 Checklist

```
命名与结构：
  □ 资源命名一致（复数、小写）
  □ 嵌套不超过 3 层
  □ 特殊操作用子资源

语义：
  □ HTTP Method 正确
  □ 状态码精确
  □ 错误格式统一

兼容：
  □ 变更是 additive 还是 breaking？
  □ breaking 是否升 major 版本？
  □ 有弃用计划和 Sunset 日期吗？

文档：
  □ OpenAPI spec 与实现同步？
  □ 有示例 request/response？
  □ 有 changelog？

安全：
  □ 认证授权覆盖所有 endpoint？
  □ 敏感字段不在 URL 中？
  □ 有限流策略吗？
```

## 附录：API 高级模式（合并自原 02_api_patterns）

### Rate Limiting

```
响应 Header：
  X-RateLimit-Limit: 1000
  X-RateLimit-Remaining: 998
  X-RateLimit-Reset: 1690000000

超限：429 Too Many Requests + Retry-After: 60

分级：匿名 100/min · 认证 1000/min · Premium 10000/min
```

### Webhook（事件回调）

```
注册：POST /api/v1/webhooks
      {"url": "https://client.com/hook", "events": ["task.created"]}

推送：POST https://client.com/hook
      X-Webhook-Signature: HMAC-SHA256(payload, secret)
      X-Webhook-Timestamp: 1690000000

重试：1min → 5min → 30min → 2h → 24h（最多 5 次）
防重放：Timestamp 5 分钟窗口 + 签名验证
```

### 批量操作

```
POST /api/v1/tasks/batch       — 批量创建
PATCH /api/v1/tasks/batch      — 批量更新
响应：{"data": {"succeeded": [...], "failed": [...]}}
```
