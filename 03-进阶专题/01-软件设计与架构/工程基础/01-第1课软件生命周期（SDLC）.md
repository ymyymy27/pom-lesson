# 第1课：软件生命周期（SDLC）

## 1. 软件生命周期是什么？

### 一句话解释
**SDLC（Software Development Life Cycle）就是软件从「想法」到「上线维护」的完整旅程** —— 像盖房子一样，先设计、再施工、再验收、再维修。

### 类比理解

| 盖房子 | 软件开发 |
|--------|---------|
| 客户需求（几室几厅） | 需求分析 |
| 可行性（预算、地皮） | 可行性分析 |
| 建筑设计图 | 系统设计 |
| 施工 | 编码实现 |
| 验收 | 测试 |
| 交付入住 | 部署上线 |
| 日常维修 | 运维与维护 |

### 为什么需要 SDLC？

没有流程：
```
客户：我要一个像淘宝一样的网站
开发：好的！（3个月后）
客户：这不是我要的...
开发：但你没说要支付功能啊
```

有流程：
```
需求 → 原型确认 → 设计评审 → 迭代开发 → 测试验收 → 上线
         ↑ 每个阶段有交付物和检查点
```

## 2. 经典 SDLC 模型

### 2.1 瀑布模型（Waterfall）

```
需求 → 设计 → 编码 → 测试 → 部署 → 维护
  ↓      ↓      ↓      ↓      ↓
文档   文档   代码   报告   上线
```

**特点：** 阶段严格顺序，前一阶段完成才进入下一阶段。

| 优点 | 缺点 |
|------|------|
| 流程清晰，文档完整 | 需求变更成本高 |
| 适合需求明确的项目 | 用户很晚才能看到成品 |
| 便于大型团队分工 | 风险集中在后期 |

**适用场景：** 政府招标项目、嵌入式系统、需求冻结的合规软件。

### 2.2 迭代模型（Iterative）

```
        ┌─→ 设计 → 编码 → 测试 ─┐
        │                       ↓
需求 ──→│←────── 评审反馈 ──────┘
        │         （多轮迭代）
        └─→ 最终产品
```

**特点：** 分多轮交付可用版本，每轮都走完整的小循环。

### 2.3 敏捷模型（Agile）— 现代主流

```
Sprint 1        Sprint 2        Sprint 3
┌─────────┐    ┌─────────┐    ┌─────────┐
│计划→开发│    │计划→开发│    │计划→开发│
│  →测试  │    │  →测试  │    │  →测试  │
│  →发布  │    │  →发布  │    │  →发布  │
└─────────┘    └─────────┘    └─────────┘
   2周            2周            2周
```

**特点：** 短周期、快速反馈、拥抱变更。详见 `learn-dev-methods/` 模块。

### 模型选型决策

```
需求是否明确且稳定？
  ├─ 是 → 是否有严格合规/文档要求？
  │        ├─ 是 → 瀑布或 V 模型
  │        └─ 否 → 迭代模型
  └─ 否 → 敏捷（Scrum/Kanban）
```

## 3. 各阶段详解

### 3.1 需求分析（Requirements）

**目标：** 搞清楚「做什么」，而不是「怎么做」。

**需求类型：**

| 类型 | 例子 | 特点 |
|------|------|------|
| 功能需求 | 用户可以注册登录 | 系统必须做什么 |
| 非功能需求 | 页面加载 < 2 秒 | 性能、安全、可用性 |
| 约束 | 必须用 Python 3.11 | 技术/法律/预算限制 |

**常用工具：**
- 用户故事（User Story）：`作为 [角色]，我希望 [功能]，以便 [价值]`
- 用例图（Use Case）
- 原型图（Wireframe / Figma）

**示例用户故事：**
```
作为 普通用户，
我希望 用邮箱和密码注册账号，
以便 使用平台的个性化功能。

验收标准：
- 邮箱格式校验
- 密码至少 8 位，含大小写和数字
- 重复邮箱提示「该邮箱已注册」
- 注册成功后自动登录
```

### 3.2 可行性分析

在投入大量开发前，回答三个问题：

1. **技术可行吗？** — 团队技能、技术栈、第三方依赖
2. **经济可行吗？** — ROI、开发成本 vs 预期收益
3. **操作可行吗？** — 用户是否愿意用、运维能否支撑

### 3.3 系统设计

**产出物：**
- 架构图（系统模块如何划分）
- 数据库 ER 图
- API 接口文档
- 技术选型说明

**设计层次：**

```
┌─────────────────────────────────────┐
│  架构设计（Architecture）            │  ← 系统级：微服务还是单体？
├─────────────────────────────────────┤
│  详细设计（Detailed Design）         │  ← 模块级：类图、时序图
├─────────────────────────────────────┤
│  接口设计（API Design）              │  ← 模块间如何通信
└─────────────────────────────────────┘
```

### 3.4 编码实现

**工程实践要点：**
- 遵循编码规范（PEP 8 / ESLint 等）
- 版本控制（Git）
- 代码审查（Code Review）
- 持续集成（CI）

### 3.5 测试

详见第3课 `03-第3课测试与质量保障.md`。此处只记核心：

```
        ┌───────┐
        │  E2E  │  少量，覆盖关键路径
        ├───────┤
        │ 集成  │  适量，模块间交互
        ├───────┤
        │ 单元  │  大量，函数/类级别
        └───────┘
           测试金字塔
```

### 3.6 部署与运维

- **部署：** 开发 → 测试 → 预发 → 生产
- **监控：** 日志、指标、告警
- **维护：** Bug 修复、功能迭代、安全补丁

## 4. 关键交付物清单

| 阶段 | 交付物 | 谁负责 |
|------|--------|--------|
| 需求 | 需求规格说明书、用户故事 | 产品/BA |
| 设计 | 架构文档、API 文档、UI 原型 | 架构师/开发 |
| 开发 | 源代码、单元测试 | 开发 |
| 测试 | 测试报告、Bug 列表 | QA |
| 部署 | 部署文档、运维手册 | DevOps |
| 维护 | 变更日志、SLA 报告 | 全员 |

## 5. 需求变更管理

变更不可避免，关键是**可控**：

```
变更请求 → 影响评估（工期/成本/风险）→ 审批 → 更新文档 → 开发
```

**变更控制原则：**
1. 所有变更必须记录（Issue / Jira Ticket）
2. 评估对已有功能的影响
3. 重大变更需重新评审设计
4. 敏捷中：变更进入 Backlog，按优先级排入 Sprint

## 6. 动手练习

### 练习 1：写用户故事

为「在线 Todo 应用」写 3 条用户故事，包含验收标准。

<details>
<summary>参考答案</summary>

```
1. 作为用户，我希望添加待办事项，以便记录要做的事。
   验收：输入标题后回车即可添加；空标题不允许。

2. 作为用户，我希望标记任务完成，以便跟踪进度。
   验收：点击复选框切换状态；已完成任务显示删除线。

3. 作为用户，我希望按优先级排序，以便先做重要的事。
   验收：支持高/中/低三档；列表默认按优先级降序。
```

</details>

### 练习 2：选型判断

以下场景分别适合哪种 SDLC 模型？说明理由。

1. 银行核心交易系统升级，需求已冻结 2 年
2. 创业公司的 MVP，每周可能改方向
3. 医疗器械软件，需通过 FDA 认证

<details>
<summary>参考答案</summary>

1. **瀑布/V 模型** — 需求明确、合规要求高、文档必须完整
2. **敏捷/Scrum** — 需求不确定、需要快速验证
3. **瀑布 + 严格 V&V** — 每个阶段需验证确认，文档可追溯

</details>
