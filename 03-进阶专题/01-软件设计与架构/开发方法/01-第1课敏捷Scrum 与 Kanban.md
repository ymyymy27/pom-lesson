# 第1课：敏捷、Scrum 与 Kanban

## 1. 敏捷宣言

2001 年，17 位软件专家提出敏捷宣言：

```
我们正在通过亲身实践和帮助他人实践，揭示更好的软件开发之道。

我们由此工作所达成的价值观是：

  个体和互动  高于  流程和工具
  可工作的软件  高于  详尽的文档
  客户合作    高于  合同谈判
  响应变化    高于  遵循计划

也就是说，尽管右项有其价值，我们更重视左项的价值。
```

### 敏捷 12 原则（精选）

1. 最高优先级是通过**早期和持续交付**有价值的软件来满足客户
2. 欢迎需求变更，即使在开发后期
3. 频繁交付可工作的软件，周期从几周到几月
4. 业务人员和开发者必须**每天一起工作**
5. 围绕 motivated 个体构建项目，给予信任和所需环境
6. 面对面交谈是最有效的沟通方式
7. **可工作的软件**是进度的主要度量
8. 可持续的开发节奏（不加班文化）
9. 持续关注技术卓越和良好设计
10. 简洁 — 最大化不做的工作
11. 自组织团队
12. 定期反思，调整行为

## 2. 敏捷 vs 瀑布

| 维度 | 瀑布 | 敏捷 |
|------|------|------|
| 计划 | 前期完整计划 | 滚动规划 |
| 交付 | 最后一次性交付 | 持续增量交付 |
| 变更 | 变更成本高 | 拥抱变更 |
| 反馈 | 晚期反馈 | 早期频繁反馈 |
| 文档 | 详尽 | 刚好够用 |
| 适用 | 需求明确、合规 | 需求不确定、创新 |

### 常见误解

| 误解 | 真相 |
|------|------|
| 敏捷 = 没有计划 | 滚动规划，每 Sprint 重新计划 |
| 敏捷 = 没有文档 | 文档刚好够用（用户故事、API 文档） |
| 敏捷 = 快 | 可持续节奏，不是赶工 |
| 敏捷 = 没有设计 | 持续设计，Emergent Design |

## 3. Scrum 框架

### 3.1 角色

| 角色 | 职责 |
|------|------|
| Product Owner (PO) | 定义做什么，管理 Product Backlog，排优先级 |
| Scrum Master (SM) | 保障流程运行，移除障碍，教练团队 |
| Development Team | 自组织完成 Sprint 目标（3–9 人） |

### 3.2 工件

```
Product Backlog          Sprint Backlog         Increment
（产品待办列表）          （Sprint 待办）         （增量）
     │                       │                    │
     │  PO 排优先级           │ Team 拆任务         │ 可工作的软件
     │                       │                    │
     └──── Sprint Planning ──┘                    │
              │                                    │
              └────── 2 周 Sprint ────────────────▷│
```

- **Product Backlog：** 所有需求的有序列表（User Story）
- **Sprint Backlog：** 当前 Sprint 承诺完成的任务
- **Increment：** Sprint 结束时交付的可工作软件

### 3.3 事件（仪式）

| 事件 | 时长（2 周 Sprint） | 目的 |
|------|-------------------|------|
| Sprint Planning | 4h | 选 Backlog 项，定 Sprint 目标 |
| Daily Standup | 15min/天 | 同步进度，暴露障碍 |
| Sprint Review | 2h | 演示 Increment，收集反馈 |
| Sprint Retrospective | 1.5h | 团队反思改进 |
| Backlog Refinement | 持续 | 细化即将做的 Story |

### 3.4 Daily Standup 三问

```
1. 昨天做了什么？
2. 今天计划做什么？
3. 有什么障碍？
```

**不是：** 向经理汇报、问题讨论会（讨论另约时间）。

### 3.5 估算：Story Point

用相对大小而非绝对时间估算：

```
Story A: 登录功能        → 3 points
Story B: 支付集成        → 8 points
Story C: 改按钮颜色      → 1 point

团队速度（Velocity）：Sprint 1 完成了 21 points
→ Sprint 2 可承诺 ~21 points 的工作量
```

**Planning Poker：** 团队同时亮牌，差异大则讨论，达成共识。

## 4. Kanban

### 核心

```
可视化工作流 + 限制在制品（WIP） + 管理流动
```

### 看板示例

```
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│ Backlog  │  To Do   │   Doing  │  Review  │   Done   │
│          │  WIP: 3  │  WIP: 2  │  WIP: 2  │          │
├──────────┼──────────┼──────────┼──────────┼──────────┤
│ Story F  │ Story C  │ Story A  │ Story B  │ Story X  │
│ Story G  │ Story D  │ Story E  │          │ Story Y  │
│ Story H  │          │          │          │          │
└──────────┴──────────┴──────────┴──────────┴──────────┘
```

### Kanban 原则

1. **可视化** — 所有工作在看板上可见
2. **限制 WIP** — 每列最多 N 项，防止多任务切换
3. **管理流动** — 关注从头到尾的流动效率
4. **明确策略** — 什么条件下进入/离开每列
5. **反馈循环** — 定期回顾
6. **实验改进** — 数据驱动优化

### Scrum vs Kanban

| | Scrum | Kanban |
|---|-------|--------|
| 迭代 | 固定 Sprint（2 周） | 持续流动 |
| 角色 | PO, SM, Team | 无强制角色 |
| 变更 | Sprint 内不变 | 随时可调整优先级 |
| 度量 | Velocity | 前置时间、吞吐量 |
| 适合 | 需要节奏和仪式 | 运维、支持、持续交付 |

**Scrumban：** 两者结合 — Sprint 节奏 + Kanban 看板。

## 5. 用户故事与 INVEST

### 用户故事格式

```
作为 [角色]
我希望 [功能]
以便 [价值/目的]
```

### INVEST 原则

| 字母 | 含义 | 说明 |
|------|------|------|
| I | Independent | 故事间尽量独立 |
| N | Negotiable | 可协商，不是合同 |
| V | Valuable | 对用户有价值 |
| E | Estimable | 可估算 |
| S | Small | 一个 Sprint 内可完成 |
| T | Testable | 有明确验收标准 |

### 故事拆分

大 Story 拆小：

```
Epic: 用户管理
├── Story: 用户注册
├── Story: 用户登录
├── Story: 修改密码
└── Story: 用户 Profile 页
```

**拆分策略：** 按工作流步骤、按业务规则、按数据类型、按 CRUD 操作。

## 6. Definition of Done（DoD）

团队对「完成」的共同定义：

```markdown
## Definition of Done
- [ ] 代码已提交并通过 CI
- [ ] 单元测试覆盖率 > 80%
- [ ] Code Review 已通过
- [ ] 文档已更新
- [ ] 在 Staging 环境验证通过
- [ ] PO 已验收
```

**DoD 保证质量一致，避免「差不多完成了」。**

## 7. 动手练习

### 练习 1：规划 Sprint

Product Backlog（已排优先级）：

| Story | Points |
|-------|--------|
| 用户注册 | 5 |
| 用户登录 | 3 |
| 商品列表页 | 8 |
| 购物车 | 5 |
| 支付集成 | 13 |

团队 Velocity = 18 points。选哪些 Story 进入 Sprint？Sprint 目标是什么？

<details>
<summary>参考答案</summary>

选：用户注册(5) + 用户登录(3) + 商品列表页(8) = 16 points  
（或 注册+登录+购物车 = 13，留 buffer）

Sprint 目标：「用户可以注册登录并浏览商品列表」

</details>

### 练习 2：设计看板

为你当前项目设计一个 Kanban 看板：列名、WIP 限制、每列的进入/退出条件。
