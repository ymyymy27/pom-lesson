# 架构设计全景图

## 1. 软件架构是什么？

### 一句话解释
**架构是系统的「蓝图」** —— 决定有哪些部分、它们如何协作、以及哪些决策难以更改。

### 架构 vs 设计

| 维度 | 架构 | 详细设计 |
|------|------|---------|
| 关注点 | 系统结构、模块边界 | 类、函数、算法 |
| 影响范围 | 全局、长期 | 局部、短期 |
| 变更成本 | 高 | 相对较低 |
| 决策者 | 架构师/Tech Lead | 开发者 |

```
架构：「用微服务还是单体？」
设计：「UserService 用什么设计模式？」
```

---

## 2. 架构师的核心职责

1. **理解需求** — 功能 + 非功能（性能、安全、可用性）
2. **做权衡** — 没有完美架构，只有合适架构
3. **定义边界** — 模块/服务如何划分
4. **记录决策** — ADR（Architecture Decision Record）
5. **指导演进** — 架构随业务成长而调整

---

## 3. 质量属性（非功能需求）

架构设计首要考虑的是**质量属性**，而非功能列表。

| 属性 | 含义 | 架构影响 |
|------|------|---------|
| 性能 | 响应时间、吞吐量 | 缓存、异步、分片 |
| 可用性 | 系统正常运行时间 | 冗余、故障转移 |
| 可扩展性 | 应对负载增长 | 水平扩展、无状态 |
| 可维护性 | 修改的容易程度 | 模块化、低耦合 |
| 安全性 | 数据与访问保护 | 认证、加密、隔离 |
| 可测试性 | 验证行为的容易程度 | DI、接口抽象 |
| 可部署性 | 发布升级的容易程度 | CI/CD、容器化 |

### 质量属性冲突

```
        性能 ←──冲突──→ 可维护性
          ↑                  ↑
          │                  │
     安全性 ←──冲突──→ 可扩展性
```

**例子：** 微服务提升可扩展性，但增加运维复杂度和网络延迟。

## 4. 常见架构风格概览

```
┌─────────────────────────────────────────────────────────┐
│                    架构风格光谱                            │
├─────────────┬──────────────┬──────────────┬─────────────┤
│   单体       │   分层/模块化  │   微服务      │  事件驱动    │
│  Monolith   │  Layered     │  Microservices│ Event-Driven│
├─────────────┼──────────────┼──────────────┼─────────────┤
│ 简单、快速    │ 清晰边界      │ 独立部署      │ 异步解耦     │
│ 难扩展       │ 适中复杂度    │ 运维复杂      │ 最终一致性   │
│ 适合早期     │ 适合中型      │ 适合大型      │ 适合高并发   │
└─────────────┴──────────────┴──────────────┴─────────────┘
```

| 风格 | 一句话 | 典型场景 |
|------|--------|---------|
| 单体 | 一个部署单元 | MVP、小团队、内部工具 |
| 分层 | 按职责水平切分 | 传统 Web 应用 |
| 六边形/整洁 | 业务核心与外部隔离 | 复杂领域逻辑 |
| 微服务 | 独立部署的小服务 | 大型团队、高扩展 |
| 事件驱动 | 通过事件异步通信 | 实时系统、数据管道 |
| Serverless | 函数即服务 | 突发流量、轻量 API |
| CQRS | 读写分离 | 读写负载差异大 |

## 5. 架构决策框架

### 5.1 选型四问

1. **团队规模和能力？** — 3 人团队不适合 20 个微服务
2. **业务阶段？** — 验证期 vs 成熟期
3. **非功能需求？** — QPS、延迟、一致性要求
4. **变更频率？** — 哪些部分变化快

### 5.2 阶段匹配

```
创业 MVP          成长期             成熟期
   │                │                  │
   ▼                ▼                  ▼
 单体/模块化    →  分层/部分拆分   →  微服务/事件驱动
 快速验证          模块边界清晰        独立扩展
```

**Martin Fowler：** 「You must be this tall to use microservices」— 团队和组织成熟度不够时不要上微服务。

## 6. 架构文档

### 6.1 C4 模型

```
Level 1: System Context  — 系统与外部用户/系统的关系
Level 2: Container       — 应用、数据库、消息队列等
Level 3: Component       — 容器内的模块
Level 4: Code            — 类图（通常 IDE 自动生成）
```

### 6.2 ADR 模板

```markdown
# ADR-001: 选择 PostgreSQL 作为主数据库

## 状态
已接受

## 背景
需要关系型数据存储，团队熟悉 SQL，需要 JSON 字段支持。

## 决策
使用 PostgreSQL 15+。

## 后果
- 正面：ACID、生态成熟、JSONB 支持
- 负面：水平扩展不如 NoSQL 灵活
- 风险：需规划读写分离方案
```

---

## 7. 架构坏味道

| 坏味道 | 表现 | 方向 |
|--------|------|------|
| 大泥球 | 无模块边界，改一处动全身 | 模块化/拆分 |
| 过度拆分 | 10 个用户搞 50 个微服务 | 合并服务 |
| 分布式单体 | 微服务部署但共享数据库 | 数据库 per service |
| 硬编码集成 | 服务间直接调用链路过长 | 事件驱动/API Gateway |
| 无监控 | 出问题不知道哪挂了 | 可观测性三件套 |

---

## 8. 可观测性三件套

```
Logs（日志）    — 发生了什么？结构化 JSON 日志
Metrics（指标） — 系统健康度？Prometheus + Grafana
Traces（追踪）  — 请求经过了谁？OpenTelemetry / Jaeger
```

**架构设计时就要考虑：** 每个服务如何输出 logs/metrics/traces，而非上线后才补。

# 附录：完整谱系 — 软件架构风格的「全家谱」

> 架构风格不是几十个孤立名词，而是**几个基本维度的组合**：
> 部署单元（一个大件 / 多个小件 / 无服务器）、模块组织（分层 / 模块化 / 插件化）、
> 通信方式（同步 / 异步 / 流）、数据策略（共享库 / 独立库 / 事件溯源）。
> 这张表是全集地图，后面的课程文件逐一深入。

## 0. 四个基本维度（一切风格的"基因"）

| 维度 | 可选值 | 影响 |
|---|---|---|
| 部署单元 | 单体 / 微服务 / 无服务器函数 / 空间网格 | 扩展粒度、部署风险 |
| 模块组织 | 分层 / 模块化 / 插件化 / 核心+边界 | 依赖方向、可维护性 |
| 通信方式 | 同步请求-响应 / 异步消息 / 事件流 | 耦合度、一致性模型 |
| 数据策略 | 共享库 / 每服务一库 / 读写分离 / 分片 / 事件溯源 | 一致性、扩展瓶颈 |

**任何"新架构"都是这四个维度的新组合。**

## 2. 风格之间的"血缘"关系

```
单体 ──加模块边界──→ 模块化单体 ──独立部署──→ 微服务
  │                      │                      │
  └──加核心边界──→ 六边形/整洁 ──加插件槽──→ 微内核/插件

请求-响应 ──加异步消息──→ 消息驱动 ──加事件流──→ EDA/事件溯源
                                                    │
                                   批处理 ──统一──→ Kappa 流式

单体数据 ──独立库──→ 每服务一库 ──读写分离/分片──→ 数据平台
                                        └──去中心──→ 数据网格
```

**启示**：大多数风格是"某个维度上把耦合再拆开一层"。学架构 =
掌握四个维度 + 看懂每个风格拆的是哪个维度。

---

## 3. 新风格判断法（三个问题）

看到一个架构（或发明一个新词），先问：

1. **它拆的是哪个维度？**（部署？模块？通信？数据？）
2. **它把复杂度搬到了哪边？**（和设计模式同一个问题）
3. **它付出了什么代价？**（没有免费的架构）

答得出 = 看懂了；答不出 = 只是换了个名字。
