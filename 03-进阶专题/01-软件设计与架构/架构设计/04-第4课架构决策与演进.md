## 1. 架构决策记录（ADR）

### 为什么需要 ADR？

```
3 个月后...
你：为什么我们用 MongoDB 不用 PostgreSQL？
同事：当时好像有人提议的...
你：？？？
```

ADR 解决**决策上下文丢失**的问题。

### ADR 模板

```markdown
# ADR-{编号}: {简短标题}

## 状态
{提议中 | 已接受 | 已废弃 | 已取代 by ADR-XXX}

## 背景
{什么问题需要决策？约束是什么？}

## 决策
{我们决定做什么？}

## 考虑的选项
| 选项 | 优点 | 缺点 |
|------|------|------|
| A    | ...  | ...  |
| B    | ...  | ...  |

## 后果
- 正面：...
- 负面：...
- 风险：...
```

### 示例

```markdown
# ADR-003: 采用 Redis 作为 Session 存储

## 状态
已接受

## 背景
Web 应用需要跨多个 API 实例共享用户 Session。
当前内存 Session 在负载均衡下无法共享。

## 决策
使用 Redis 存储 Session，TTL 24 小时。

## 考虑的选项
| 选项 | 优点 | 缺点 |
|------|------|------|
| Sticky Session | 无额外组件 | 实例宕机丢 Session |
| Redis | 快速、成熟 | 多一个依赖 |
| JWT 无状态 | 无存储 | 难撤销、Token 较大 |

## 后果
- 正面：Session 共享、毫秒级读写
- 负面：Redis 故障影响登录态
- 风险：需 Redis 高可用（Sentinel/Cluster）
```

### ADR 最佳实践

- 存在 `docs/adr/` 目录，版本控制
- 编号递增，不删除旧 ADR（标记「已取代」）
- 决策时写，而非事后补
- 保持简短（1-2 页）

## 2. 架构评估方法

### 2.1 ATAM（Architecture Tradeoff Analysis Method）

```
1. 确定业务驱动因素（质量属性优先级）
2. 描述架构方案
3. 生成质量属性效用树
4. 分析架构方法
5. 识别风险和非风险
6. 输出评估报告
```

### 2.2 效用树示例

```
性能
├── 响应时间
│   ├── 搜索 < 200ms（H）  ← H=高优先级
│   └── 下单 < 1s（H）
├── 吞吐量
│   └── 10000 QPS（M）
可用性
├── 99.9% SLA（H）
└── 故障恢复 < 5min（M）
```

### 2.3 架构评审清单

- [ ] 单点故障？有冗余吗？
- [ ] 瓶颈在哪？如何扩展？
- [ ] 数据一致性要求？如何保障？
- [ ] 安全措施？认证、加密、审计？
- [ ] 监控告警？出问题如何发现？
- [ ] 部署策略？蓝绿/金丝雀/滚动？
- [ ] 回滚方案？
- [ ] 技术债？已知妥协？

## 3. 扩展性设计

### 3.1 扩展维度

```
         垂直扩展（Scale Up）          水平扩展（Scale Out）
         换更强的机器                   加更多机器
         ┌─────────┐                  ┌───┐ ┌───┐ ┌───┐
         │  128GB  │                  │ 4G│ │ 4G│ │ 4G│
         │  32 CPU │                  └───┘ └───┘ └───┘
         └─────────┘                  + LB 负载均衡
         有上限                        理论无限
```

**云原生首选水平扩展。**

### 3.2 无状态设计

```
有状态：Session 存在服务器内存 → 无法随意扩展
无状态：Session 存 Redis / JWT → 任意实例可处理
```

### 3.3 扩展策略

| 组件 | 扩展方式 |
|------|---------|
| Web/API | 水平 + 负载均衡 |
| 数据库 | 读写分离 → 分片 |
| 缓存 | Redis Cluster |
| 消息队列 | 增加 Partition |
| 文件存储 | 对象存储（S3/OSS） |

### 3.4 性能优化层次

```
1. 算法/数据结构     ← 影响最大
2. 缓存              ← 减少重复计算/查询
3. 异步/批处理        ← 减少等待
4. 数据库优化         ← 索引、查询优化
5. 水平扩展           ← 加机器
6. 垂直扩展           ← 最后手段
```

## 4. 安全架构

### 4.1 纵深防御

```
Internet → WAF → Load Balancer → API Gateway
    → AuthN/AuthZ → Service → Database
         每层都有安全控制
```

### 4.2 核心实践

| 实践 | 说明 |
|------|------|
| 最小权限 | 服务/用户只给必要权限 |
| 传输加密 | HTTPS/TLS everywhere |
| 静态加密 | 数据库、存储加密 |
| Secret 管理 | Vault / K8s Secrets，不入代码 |
| 输入验证 | 防 SQL 注入、XSS |
| 审计日志 | 谁做了什么，可追溯 |

### 4.3 Zero Trust

> 永不信任，始终验证。

- 服务间也需 mTLS 认证
- 网络分段（微隔离）
- 持续验证身份

## 5. 架构演进策略

### 5.1 绞杀者无花果（Strangler Fig）

逐步用新系统替换旧系统，而非一次性重写。

```
Phase 1: 旧系统 100%
Phase 2: 新功能走新系统，旧功能仍走旧系统
Phase 3: 逐步迁移旧功能
Phase 4: 旧系统下线
```

```
         ┌──────────┐
Client ─▷│  Facade  │ ← 路由层决定走新还是旧
         └────┬─────┘
         ┌────┴─────┐
         ▼          ▼
    Old System  New System
    (shrinking) (growing)
```

### 5.2 分支 by 抽象（Branch by Abstraction）

```
1. 创建抽象接口
2. 旧实现适配到接口
3. 新实现适配到接口
4. 切换实现
5. 删除旧实现
```

### 5.3 演进路径示例

```
Year 1: 单体 + PostgreSQL
         ↓ 用户量增长
Year 2: 模块化单体 + Redis 缓存 + 读写分离
         ↓ 搜索成为瓶颈
Year 3: 搜索服务独立 + Elasticsearch
         ↓ 团队扩大
Year 4: 核心服务微服务化 + 消息队列
         ↓ 全球化
Year 5: 多区域部署 + CDN + Event Sourcing（审计）
```

**关键：** 每一步都因**真实的痛点**驱动，而非追技术潮流。

## 6. 架构与技术债

### 有意识的妥协

```
ADR-005: 暂时用 SQLite 而非 PostgreSQL

背景：MVP 阶段，0→1 验证
决策：SQLite，3 个月内迁移
后果：迁移成本可接受，加速上线
```

### 技术债分类

| 类型 | 示例 | 处理 |
|------|------|------|
| 故意/有记录 | ADR 中的已知妥协 | 按计划偿还 |
| 无意/未发现 | 无测试的代码 | 发现后评估 |
| 过时 | 旧框架版本 | 定期升级 |

# 深入篇：架构决策与演进的底层逻辑

## 1. ADR 的深层：记录的是"为什么"，不是"做了什么"

ADR 的真正价值不是文档，而是**让未来的决策有上下文**：

```
三个月后有人问"为什么用 MongoDB？"
  ADR：当时 Postgres 的 JSONB 不够快、团队没人懂运维 PG、数据模型会变
  → 这是"可讨论的决策"
没有 ADR："好像当时有人提议的……"
  → 这是"不可讨论的迷信"
```

**反形式主义三条**：

1. **决策时写**，不是事后补——事后补的 ADR 是编历史；
2. **写明触发条件**（什么时候 revisit）——让技术债"有还期"；
3. **ADR 要有寿命**——被取代就标记"已取代 by ADR-XXX"，不删除。

**ADR 的核心问题清单**：

- 这个决策解决什么问题？（背景）
- 我们选了什么？为什么不是别的？（选项对比）
- 代价是什么？风险是什么？（后果）
- 什么信号出现时要重新评估？（触发条件）

## 2. 架构评估的深层：ATAM 在评估什么

ATAM 不是"评审代码"，而是回答三个问题：

1. **业务到底要什么质量？**（把模糊的"要稳定"变成"99.9% 可用性"）
2. **架构方案能满足吗？**（效用树：质量属性 → 场景 → 优先级）
3. **哪些决策是"风险点"？**（敏感点：决定成败的权衡点）

实战判断：**一个架构评估如果不产生"风险清单"，等于没评。**
输出必须是一份"哪些地方可能在将来杀死我们"的清单，而不是打分。

## 3. 扩展性的深层：无状态为什么是水平扩展的前提

```
有状态实例：Session 在内存 → 请求必须回原实例 → 无法随意扩缩
无状态实例：状态外置（Redis/JWT/DB） → 任意实例可处理 → 扩缩随意
```

**状态外置的三种方式**：

| 方式 | 适用 |
|---|---|
| 外置存储（Redis/DB） | 会话、配置、通用状态 |
| 无状态 Token（JWT） | 可自包含、不需要撤销的场景 |
| 粘性会话（Sticky Session） | 过渡方案——实例挂 = 丢状态，别长期用 |

**扩展的优先级顺序（从便宜到贵）**：

```
1. 优化算法/查询（最便宜）
2. 缓存（减少重复计算）
3. 异步化（减少等待）
4. 读写分离（拆数据负载）
5. 水平扩展（加实例——前提是无状态）
6. 分片（最后手段，不可逆）
```

## 4. 演进策略的深层：绞杀者的三种变体

绞杀者不是"一种"改法，是"渐进替换"的家族：

| 变体 | 做法 | 适用 |
|---|---|---|
| 路由绞杀 | 网关按请求路由新旧 | 按功能模块迁移 |
| 适配器绞杀 | 旧系统包适配器暴露新接口 | 接口先统一、实现后换 |
| 冒泡绞杀 | 旧系统内部逐步长出"新系统气泡" | 无法整体替换的大泥球 |

**演进铁律**：

1. **每个阶段都可上线、可回滚**——没有"切换日"，只有"灰度日"；
2. **由真实痛点触发**，不是"架构升级 KPI"；
3. **数据迁移是最难的部分**——先迁数据再切流量，或双写过渡。

## 5. 安全的深层：为什么是"纵深防御"

任何一层都可能被打穿，所以**每层都要有控制**：

```
互联网 → WAF → LB → 网关（认证/限流） → 服务（授权/输入验证）
       → 数据（加密/审计） → 基础设施（网络分段）
```

零信任的核心不是"更严格的防火墙"，而是**默认不信**：

- 内网流量也要 mTLS（服务间身份）；
- 每个请求都要验证（不只边界一次）；
- 最小权限（服务只拿需要的凭证）。

**AI 时代新增的攻击面**（详见 `learn-security/04_llm_and_agent_security.md`）：

- 提示注入（外部输入污染系统提示）；
- 工具滥用（Agent 拿到不该有的工具 = 越权）；
- 数据泄漏（上下文里的敏感信息随回答外泄）；
- 供应链（模型、插件、依赖的投毒）。

## 6. 演进实战：一个 5 年架构演进的"为什么"

```
Year 1：单体 + SQLite → 为什么？验证产品，最小成本
Year 2：PostgreSQL + Redis → 为什么？用户增长，数据可靠性与热点缓存
Year 3：模块化单体 → 为什么？团队 3→8 人，冲突开始出现
Year 4：搜索独立 → 为什么？搜索 CPU 占 80%，其他 5%（扩展曲线不同）
Year 5：订单服务化 + Kafka → 为什么？支付合规隔离 + 多下游事件
```

每一步的"为什么"都是**真实的痛**：部署太慢、扩展失衡、合规要求、团队冲突。
架构演进的本质不是"升级"，是"用最小的成本解除当前最大的约束"。

**核心心法**：架构决策 = 当前约束 × 可预见的下一步。
永远不要为"三年后可能"买单——要为"下一季度必然"买单。
