## 1. 无服务器架构（Serverless / FaaS）

### 1.1 原理

核心思想一句话：**按函数粒度弹性运行，平台替你管服务器。**

```
传统微服务：                       无服务器：
┌───────────────────┐             ┌─────────────────────┐
│ 常驻进程（一直付钱）│             │ 函数（按调用计费）      │
│ 你自己扩缩容        │    vs.      │ 平台自动扩缩到 0       │
│ 你自己管补丁/高可用  │             │ 平台管一切基础设施      │
└───────────────────┘             └─────────────────────┘
```

两个核心概念：

| 概念 | 说明 |
|---|---|
| FaaS（函数即服务） | 你只写函数（AWS Lambda、Cloud Functions），平台负责运行 |
| BaaS（后端即服务） | 认证、数据库、存储等直接以服务形式提供（Supabase、Firebase） |

隔离的变化：**运行环境与容量**。你只管"处理逻辑"，扩缩容、高可用、补丁全交给平台。

关键特性：

1. **冷启动**：函数首次调用要初始化运行时（几百毫秒到几秒）；
2. **无状态铁律**：函数不假设有本地状态，状态放外部（DB/Redis/对象存储）；
3. **按调用计费**：空闲时零成本——"缩容到 0"是无服务器的最大卖点。

### 1.2 代码分析

```python
# AWS Lambda 风格（概念示意）
import json

def handler(event: dict, context) -> dict:
    """一个无状态函数：输入事件，输出结果"""
    body = json.loads(event.get("body", "{}"))
    user_id = body.get("user_id")

    # 状态必须放外部——函数实例随时会被销毁
    profile = user_table.get(user_id)          # BaaS 数据库

    return {
        "statusCode": 200,
        "body": json.dumps({"profile": profile}),
    }

# 事件驱动接入：S3 上传 → 触发函数 → 处理 → 写回
def on_file_uploaded(event: dict, context) -> None:
    bucket = event["Records"][0]["s3"]["bucket"]["name"]
    key = event["Records"][0]["s3"]["object"]["key"]
    process_file(bucket, key)                  # 无服务器最擅长：事件触发
```

读代码只看三个点：

1. 函数**没有全局状态**——实例随时重建；
2. 一切依赖通过参数传入（event/context）或外部服务；
3. 典型接入方式是**事件触发**（对象存储上传、消息队列、定时器）。

### 1.3 实战解析

**何时用：**

- 间歇性/突发性负载（用量起伏大，常驻进程浪费）；
- 事件触发的短任务（图片处理、文件转换、通知发送）；
- 小团队想省运维成本；
- AI 场景：异步推理回调、批量 embedding 作业、Webhook 处理。

**何时别用：**

- 长连接/WebSocket 服务（函数寿命有限）；
- 高 QPS 稳定负载（冷启动 + 按调用计费反而更贵）；
- 有状态、需要本地缓存的服务；
- 对冷启动延迟敏感的核心链路。

**代价：**

- 冷启动延迟不可控；供应商锁定；
- 调试困难（无本地环境、日志分散）；
- 分布式"函数爆炸"——每个函数是一个部署单元，可观测性成本高。

## 2. 流式处理架构（Lambda / Kappa）

### 2.1 原理

核心思想一句话：**数据处理要么走批、要么走流——Kappa 说"只有流"。**

两种经典模式：

```
Lambda 架构（双轨）：
  实时层：事件 → 流处理 → 实时视图（快但可能不准）
  批处理层：全量数据 → 批处理 → 批视图（准但慢）
  合并查询：两个视图合并 → 最终答案

Kappa 架构（单轨）：
  一切皆流：所有数据先进事件流（Kafka），流处理器产出视图
  重算 = 从 offset 0 重放事件流，不另建批处理系统
```

关键洞察：

1. **批是流的特例**——把"无限流"在时间窗口上切一刀就是批；
2. 流处理器的核心是**有状态窗口**（滚动窗口、会话窗口）；
3. 事件流的**可重放性**（offset）让"重算"成为可能——这是 Kappa 的底气。

### 2.2 代码分析

```python
# 流处理概念（Flink/Spark Streaming 风格的简化示意）
class StreamProcessor:
    def __init__(self):
        self._state: dict[str, int] = {}   # 窗口状态：key → 计数

    def process_event(self, event: dict) -> None:
        key = event["tenant_id"]
        self._state[key] = self._state.get(key, 0) + 1

    def snapshot(self) -> dict:
        return self._state                  # 产出当前视图

# 重放：Kappa 的关键能力
class EventLog:
    """只追加的事件日志，支持从任意 offset 重放"""
    def __init__(self):
        self._events: list[dict] = []
    def append(self, event: dict) -> int:
        self._events.append(event)
        return len(self._events) - 1        # 返回 offset
    def replay(self, from_offset: int = 0):
        for i, e in enumerate(self._events):
            if i >= from_offset:
                yield e

# 重算视图 = 清空状态 + 从 0 重放
log = EventLog()
log.append({"tenant_id": "a"})
log.append({"tenant_id": "b"})
log.append({"tenant_id": "a"})

p = StreamProcessor()
for e in log.replay(0):                     # 重放 → 视图可复现
    p.process_event(e)
print(p.snapshot())  # {"a": 2, "b": 1}
```

### 2.3 实战解析

**何时用：**

- 实时指标/仪表盘（QPS、错误率、业务漏斗）；
- 用户行为流（点击流 → 特征 → 推荐/风控）；
- CDC（数据库变更捕获 → 下游同步，如 Debezium → Kafka）；
- AI 场景：实时特征、流式推理、在线学习。

**Lambda vs Kappa 怎么选：**

| | Lambda | Kappa |
|---|---|---|
| 复杂度 | 高（两套系统） | 低（一套流） |
| 准确性 | 批处理保证精确重算 | 依赖流处理器的状态一致性 |
| 场景 | 历史遗留、批需求强 | 新系统、流为主 |

**现代倾向：** 新项目优先 Kappa；只有"周期性全量报表"这类强批需求才考虑 Lambda。

**代价：**

- 流处理的**状态管理**是难点（窗口、水位线、故障恢复）；
- 事件 schema 演进要兼容历史重放；
- 调试时间敏感逻辑比批处理难得多。

## 3. 服务网格（Service Mesh）

### 3.1 原理

核心思想一句话：**把服务间通信的"脏活"下沉到代理层，业务代码只管业务。**

微服务多了之后，每个服务都要重复实现：重试、超时、熔断、限流、TLS、
可观测性（指标/追踪）、金丝雀发布……服务网格把这些能力从**业务进程**里抽出来，
放进伴随每个服务实例的 **Sidecar 代理**：

```
┌─────────────────────────┐      ┌─────────────────────────┐
│ Service A                │      │ Service B                │
│ ┌──────┐   ┌──────────┐ │      │ ┌──────────┐   ┌──────┐ │
│ │ 业务  │──▶│ Sidecar  │─┼─────▶│ │ Sidecar  │──▶│ 业务  │ │
│ └──────┘   │ (Envoy)  │ │  mTLS │ (Envoy)  │   └──────┘ │
│            └──────────┘ │  HTTP2 │ └──────────┘           │
└─────────────────────────┘      └─────────────────────────┘
                    ▲ 控制面（Istio: 规则下发、证书、遥测）
```

两个平面：

| 平面 | 职责 |
|---|---|
| 数据面（Data Plane） | Sidecar 代理：实际转发流量、执行重试/熔断/限流 |
| 控制面（Control Plane） | 下发配置、签发证书、收集遥测（Istiod/Pilot） |

隔离的变化：**通信的非业务能力**。加熔断/灰度/加密 = 改配置，业务代码零改动。

### 3.2 代码分析（概念）

```yaml
# Istio VirtualService：金丝雀发布 10% 流量到 v2
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: checkout
spec:
  hosts:
    - checkout
  http:
    - match:
        - headers:
            canary: "true"        # 按请求头路由
      route:
        - destination: { host: checkout, subset: v2 }
    - route:
        - destination: { host: checkout, subset: v1 }
          weight: 90
        - destination: { host: checkout, subset: v2 }
          weight: 10              # 10% 流量到新版
```

```python
# 业务代码视角：服务网格透明之后，这就是全部
async def checkout(user_id: str):
    # 重试、超时、mTLS、追踪……全由 Sidecar 处理
    return await call("inventory", {"user_id": user_id})
```

读代码只看一点：**业务进程里没有任何重试/熔断/TLS 代码**——
这些能力全部声明在网格配置里，由 Sidecar 执行。

### 3.3 实战解析

**何时用：**

- 服务数量多（一般 30+），通信能力重复实现成本高；
- 需要统一的可观测性（每个调用自动有 trace/指标）；
- 需要精细的流量治理（灰度、AB、故障注入）。

**何时别用：**

- 服务少（<10）——网格的运维成本超过收益；
- 团队没有能力运维控制面（Istio 本身是复杂系统）；
- 性能极其敏感（Sidecar 增加一跳网络开销）。

**代价：**

- 新增一个复杂基础设施（控制面高可用本身是工程）；
- 排障要同时看业务日志和 Sidecar 日志；
- 供应商锁定（Istio/Linkerd/Consul Connect 各有各的坑）。

**与无服务器的关系：** 两者都是"把复杂度移出业务代码"——
无服务器移走的是运行时，服务网格移走的是通信能力。

# 深入篇：现代运行族的底层逻辑

## 1. 无服务器的深层：把「容量规划」外包给云

FaaS 的真正价值不是省钱，是 **把扩缩容决策从应用团队移走**。
代价是冷启动、执行时长限制、调试与供应商锁定——适合「事件触发的短任务」，不适合「常驻连接」。

## 2. 流式的深层：批是流的特例

Kappa 的哲学：**同一套事件流既能实时消费，也能按 offset 重放当批处理**。
Lambda 双轨适合历史包袱重的团队； greenfield 可优先考虑 Kappa + 重放。

## 3. 服务网格的深层：通信策略产品化

Sidecar 把重试、熔断、mTLS、金丝雀从业务代码里 **抽成基础设施策略**。
团队 < 5 个微服务时，库级 resilience（如 resilience4j）通常够用；网格在 **多语言、多团队** 时 ROI 才显现。
