# 系统设计方法论

## 1. 系统设计是什么？

### 一句话解释
**在给定约束下，设计可扩展、可靠、可维护的软件系统** —— 回答「用什么组件、怎么交互、为什么这样选」。

### 系统设计 vs 架构设计

| 维度 | 架构设计 | 系统设计 |
|------|---------|---------|
| 视角 | 长期演进、组织匹配 | 具体场景、容量与组件 |
| 产出 | ADR、上下文地图 | 架构图、API、数据模型 |
| 场景 | 产品架构评审 | 技术面试、新项目立项 |

**本模块侧重：** 45–60 分钟内完成 high-level design 的实战能力。

---

## 2. 设计流程（RADIO 框架）

```
R — Requirements（需求）
    功能需求 + 非功能需求（QPS、延迟、可用性）

A — Architecture（架构）
    核心组件 + 数据流 + 存储选型

D — Data（数据）
    数据模型、分区、缓存、一致性

I — Interface（接口）
    API 设计、关键 endpoint

O — Optimizations（优化）
    瓶颈、扩展、权衡、失败模式
```

### 时间分配（45 分钟）

| 阶段 | 时间 | 产出 |
|------|------|------|
| 澄清需求 | 5 min | 功能列表 + 非功能数字 |
| 容量估算 | 5 min | QPS、存储、带宽 |
| High-level 设计 | 15 min |  boxes + arrows 架构图 |
| 深入 2–3 组件 | 15 min | DB schema、缓存、热点 |
| 权衡与扩展 | 5 min | 瓶颈、单点、监控 |

---

## 3. 需求澄清清单

### 功能需求（必问）

- 核心用户场景是什么？（写、读、还是两者？）
- 有哪些实体？（User、Post、Order...）
- 是否需要实时？搜索？推荐？

### 非功能需求（必问数字）

| 问题 | 示例答案 |
|------|---------|
| 日活/月活？ | 1000 万 DAU |
| 读写比例？ | 100:1 |
| 延迟要求？ | p99 < 200ms |
| 可用性？ | 99.9% |
| 数据保留？ | 永久 / 90 天 |
| 一致性？ | 强一致 / 最终一致 |

**技巧：** 如果没有给定数字，主动假设并说明：「假设 1000 万 DAU，我按此估算...」

---

## 4. 架构图绘制规范

### 基本元素

```
┌─────────┐     ┌─────────┐     ┌─────────┐
│ Client  │────▷│   LB    │────▷│ API Svc │
└─────────┘     └─────────┘     └────┬────┘
                                     │
                    ┌────────────────┼────────────────┐
                    ▼                ▼                ▼
              ┌──────────┐    ┌──────────┐    ┌──────────┐
              │  Cache   │    │    DB    │    │   MQ     │
              └──────────┘    └──────────┘    └──────────┘
```

### 层次

1. **L1：** Client → LB → Service → Storage（5 分钟必画）
2. **L2：** 服务拆分、缓存层、异步队列
3. **L3：** 分片、副本、CDN（深入时再画）

**不要一开始就画细节** — 先 L1 确认方向，再逐层深入。

## 5. 常见组件选型

| 需求 | 常见选型 |
|------|---------|
| 关系数据 | PostgreSQL, MySQL |
| 文档存储 | MongoDB |
| 缓存 | Redis, Memcached |
| 搜索 | Elasticsearch |
| 消息队列 | Kafka, RabbitMQ |
| 对象存储 | S3, OSS |
| CDN | CloudFront, Cloudflare |
| 负载均衡 | Nginx, ALB, K8s Ingress |

**原则：** 说出选型理由，而非只报名字。

---

## 6. 扩展性基本模式

| 模式 | 说明 | 何时 |
|------|------|------|
| 水平扩展 | 加机器 + LB | 无状态服务 |
| 读写分离 | Master + Replicas | 读多写少 |
| 缓存 | Redis 挡 DB | 热点读 |
| 分片 | 按 key 分区 | 单库放不下 |
| 异步 | MQ 解耦 | 非实时、削峰 |
| CDN | 静态/边缘缓存 | 全球用户 |

---

## 7. 可靠性基本模式

| 模式 | 说明 |
|------|------|
| 冗余 | 多副本、多 AZ |
| 熔断 | 下游故障快速失败 |
| 限流 | 保护核心服务 |
| 降级 | 关非核心功能保核心 |
| 重试 + 幂等 | 网络不可靠 |
| 健康检查 | LB 剔除故障节点 |

## 8. 设计评审自检

- [ ] 单点故障？每个组件有备份吗？
- [ ] 瓶颈在哪？DB？网络？CPU？
- [ ] 10 倍流量怎么办？
- [ ] 数据丢失怎么办？备份策略？
- [ ] 如何监控和告警？
- [ ] 安全：认证、授权、加密？

## 9. 动手练习

### 练习：5 分钟设计「待办事项 App」

假设 10 万 DAU，列出：功能需求、非功能需求、L1 架构图组件。

<details>
<summary>参考答案（概要）</summary>

**功能：** CRUD 待办、列表、完成标记、用户隔离  
**非功能：** 10 万 DAU ≈ 12 QPS 平均（峰值 100），p99 < 500ms  
**架构：** Mobile/Web → LB → Todo API → PostgreSQL + Redis（session/热点列表）

</details>
