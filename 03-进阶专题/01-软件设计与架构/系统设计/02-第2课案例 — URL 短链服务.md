# 第2课：案例 — URL 短链服务

> 经典系统设计入门题。建议先限时 30 分钟自己设计，再阅读本文。

## 1. 需求澄清

### 功能需求

```
- 输入长 URL，返回短 URL
- 访问短 URL，302 重定向到长 URL
- 可选：自定义短码、过期时间、访问统计
```

### 非功能需求（假设）

| 指标 | 假设值 |
|------|--------|
| 新建短链 | 1000 写 QPS |
| 重定向读 | 10 万读 QPS（100:1 读写比） |
| 延迟 | 重定向 p99 < 100ms |
| 可用性 | 99.9% |
| 短链长度 | 7 字符 |

---

## 2. 容量估算

```
写 QPS：1000/s
读 QPS：100,000/s（峰值 ×3 → 30 万/s）

存储（5 年）：
  1000 × 86400 × 365 × 5 ≈ 1570 亿条
  每条 ~500 bytes（短码 + 长 URL + 元数据）
  ≈ 785 TB → 需要分片

带宽（读为主）：
  30 万 QPS × 500 bytes ≈ 150 MB/s
```

## 3. High-Level 架构

```
                    ┌─────────────┐
  Client ──POST──→  │  API Server  │ ──→ 写入 DB
  (创建短链)         └─────────────┘
                           │
                    ┌──────┴──────┐
                    │  Short Code  │
                    │  Generator   │
                    └─────────────┘

  Client ──GET──→  ┌─────────────┐     Cache Miss
  (访问短链)        │  Redirect    │ ──→ DB Lookup
                    │  Service     │
                    └──────┬──────┘
                           │
                    ┌──────┴──────┐
                    │    Redis     │  ← 热点短链缓存
                    │   (Cache)    │
                    └─────────────┘
```

## 4. 核心设计：短码生成

### 方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 自增 ID + Base62 | `12345 → "dnh"` | 无冲突、有序 | 可预测、需中心化 ID |
| MD5 截断 | hash(url)[:7] | 同 URL 同短码 | 冲突需处理 |
| 随机 + 冲突检测 | random Base62，冲突重试 | 简单 | 高 QPS 时冲突多 |

**推荐：自增 ID + Base62**

```python
BASE62 = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def encode(num: int) -> str:
    if num == 0:
        return BASE62[0]
    result = []
    while num:
        result.append(BASE62[num % 62])
        num //= 62
    return "".join(reversed(result))

# 123456789 → "8m0Kx"
```

```
7 位 Base62 = 62^7 ≈ 3.5 万亿 种组合，足够用

ID 生成：Snowflake / DB auto-increment / Redis INCR
```

### 自定义短码

```
用户提交自定义码 → 查重 → 冲突则 409 Conflict
自定义码不走自增，直接作为主键存储
```

## 5. 数据模型

```sql
CREATE TABLE urls (
    id          BIGINT PRIMARY KEY,       -- 自增 ID
    short_code  VARCHAR(10) UNIQUE NOT NULL,
    long_url    TEXT NOT NULL,
    user_id     BIGINT,
    created_at  TIMESTAMP DEFAULT NOW(),
    expires_at  TIMESTAMP,                 -- NULL = 永不过期
    click_count BIGINT DEFAULT 0
);

CREATE INDEX idx_short_code ON urls(short_code);
```

**分片策略：** 按 `short_code` hash 分片（读多写少，均匀分布）

---

## 6. 读路径优化（重点）

读 QPS 是写的 100 倍，缓存是核心：

```
Cache-Aside 策略：

  GET /{short_code}:
    1. 查 Redis → 命中 → 302 重定向
    2. Miss → 查 DB → 写入 Redis（TTL 24h）→ 302

  热点 URL（微博热搜链接）：
    - 本地缓存（进程内 LRU）+ Redis 两级缓存
    - 预加载已知热点
```

### 302 vs 301

| 状态码 | 行为 | 适用 |
|--------|------|------|
| 301 | 永久重定向，浏览器缓存 | 短链不变、要 SEO |
| 302 | 临时重定向，每次请求服务器 | 需要统计点击量 |

**短链服务通常用 302**（要统计访问、支持 URL 变更）

---

## 7. 扩展与权衡

### 单点故障

```
- API Server：无状态，水平扩展 + LB
- Redis：主从 + Sentinel 或 Cluster
- DB：主从复制，读走从库
```

### 过期清理

```
方案1：Lazy — 访问时发现过期，删除并返回 410
方案2：Active — 定时任务扫描 expires_at
推荐：Lazy + 每周批量清理
```

### 安全

```
- 防止恶意长 URL（钓鱼）：黑名单 + Google Safe Browsing API
- Rate Limit：每 IP 每分钟最多创建 10 条
- 短码不可预测：自增 ID 加 salt 或随机 offset
```
