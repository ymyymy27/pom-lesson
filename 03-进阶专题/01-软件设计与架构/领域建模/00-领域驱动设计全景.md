# 领域驱动设计全景

## 1. DDD 是什么？

### 一句话解释
**DDD（Domain-Driven Design）是用业务语言构建软件模型的方法** —— 让代码结构反映真实业务，而非数据库表结构。

### 类比理解

| 盖房子 | DDD |
|--------|-----|
| 先了解住户需求和生活习惯 | 深入理解业务领域 |
| 按「客厅、卧室、厨房」划分功能区 | 按业务能力划分限界上下文 |
| 用住户能懂的话沟通（「玄关」而非「入口缓冲区」） | 通用语言（Ubiquitous Language） |
| 承重墙不能随意拆 | 聚合不变量 |

### 为什么需要 DDD？

没有 DDD：
```
数据库表：users, orders, order_items, payments, ...
代码结构：完全镜像数据库
业务说：「订单取消后要释放库存并退款」
代码：在 OrderController 里写 200 行 if/else，调用 5 个 Service
```

有 DDD：
```
限界上下文：订单、库存、支付 各自独立
通用语言：「取消订单」→ CancelOrder 命令 → OrderCancelled 领域事件
         → 库存上下文订阅 → 释放库存
         → 支付上下文订阅 → 发起退款
```

## 2. 战略设计 vs 战术设计

```
┌─────────────────────────────────────────────────────────┐
│                    DDD 两大层次                           │
├────────────────────────┬────────────────────────────────┤
│      战略设计           │           战术设计              │
│  （宏观：系统怎么拆）     │    （微观：代码怎么写）          │
├────────────────────────┼────────────────────────────────┤
│  限界上下文             │  实体 Entity                   │
│  上下文地图             │  值对象 Value Object           │
│  通用语言               │  聚合 Aggregate                │
│  子域 Subdomain         │  Repository                    │
│  防腐层 ACL             │  Domain Event                  │
│  发布语言               │  应用服务 Application Service  │
└────────────────────────┴────────────────────────────────┘
```

**学习顺序：** 先战略（划分边界），再战术（边界内建模）。

## 3. 子域分类

| 类型 | 含义 | 策略 |
|------|------|------|
| 核心域 Core | 竞争优势所在 | 自研、投入最多 |
| 支撑域 Supporting | 必需但非差异化 | 自研但简化 |
| 通用域 Generic | 行业通用能力 | 买/用开源（如认证、支付网关） |

**示例（电商）：**

```
核心域：  推荐算法、定价引擎、供应链优化
支撑域：  订单管理、库存管理
通用域：  用户认证、短信通知、支付通道
```

**启示：** 不要在通用域过度设计；核心域才值得 DDD 深度建模。

## 4. 限界上下文（Bounded Context）

### 定义
模型的**显式边界**，边界内术语和规则一致，边界外可能同名不同义。

### 同名不同义示例

| 词 | 销售上下文 | 物流上下文 | 财务上下文 |
|----|-----------|-----------|-----------|
| Product | 可售 SKU、价格 | 重量、体积 | 成本、利润 |
| Customer | 买家、会员等级 | 收件人、地址 | 应收账款方 |

**错误做法：** 一个 `Product` 类包含所有字段 → 上帝对象  
**正确做法：** 每个上下文有自己的 `Product` 模型，通过 ID 关联

### 识别限界上下文的方法

1. **按业务能力** — 用户管理、订单、支付、搜索
2. **按组织团队** — Conway's Law，团队边界 ≈ 上下文边界
3. **按变更频率** — 变化节奏不同的放不同上下文
4. **按数据一致性** — 需要强一致的一起，可最终一致的分开

## 5. 上下文地图（Context Map）

描述上下文之间的**关系**。

```
                    ┌──────────────┐
                    │   销售 Sales  │（核心）
                    └──────┬───────┘
                           │ 客户/供应商 Customer-Supplier
              ┌────────────┼────────────┐
              ▼            ▼            ▼
       ┌──────────┐  ┌──────────┐  ┌──────────┐
       │  库存     │  │  支付     │  │  物流     │
       │ Inventory│  │ Payment  │  │ Shipping │
       └──────────┘  └──────────┘  └──────────┘
              ▲                           │
              └─────── 防腐层 ACL ─────────┘
                    （物流用外部 API，需翻译）
```

### 上下文关系类型

| 关系 | 说明 | 示例 |
|------|------|------|
| Partnership | 两个上下文共同成功/失败 | 订单 + 支付联合迭代 |
| Shared Kernel | 共享一小部分模型 | 共享 UserId 值对象 |
| Customer-Supplier | 上游为下游提供 API | 销售 → 库存 |
| Conformist | 下游完全适配上游 | 用第三方物流 API |
| Anti-Corruption Layer | 下游翻译上游模型 | 隔离外部系统污染 |
| Open Host Service | 上游提供标准协议 | 公开 REST API |
| Published Language | 共享事件/协议格式 | 统一 Event Schema |

## 6. 通用语言（Ubiquitous Language）

### 原则
开发、产品、业务用**同一套术语**，且术语直接体现在代码中。

```
❌ 业务：「用户下单后进入待发货状态」
   代码：order.status = 2

✅ 业务：「用户下单后进入待发货状态」
   代码：order.mark_as_pending_shipment()
         或 order.transition_to(PendingShipment)
```

### 实践

- 事件风暴（Event Storming）工作坊：业务 + 开发一起贴便利贴
- 代码审查时检查命名是否与通用语言一致
-  glossary.md 维护术语表

## 7. 何时引入 DDD？

### 适合

| 信号 | 说明 |
|------|------|
| 业务复杂 | 规则多、变化快、领域专家可用 |
| 长期演进 | 系统会存在 3 年以上 |
| 多团队协作 | 需要清晰边界 |
| 核心域 | 竞争优势在业务逻辑 |

### 不适合

| 信号 | 说明 |
|------|------|
| CRUD 为主 | 简单增删改查，无复杂规则 |
| 技术探索/MVP | 快速验证，业务未定型 |
| 小团队小项目 | 1–3 人，过度设计 |
| 通用域 | 直接用 SaaS/开源 |

### 渐进引入

```
Level 0: 贫血模型 + 事务脚本（大多数项目起点）
Level 1: 通用语言 + 限界上下文划分（低成本高收益）
Level 2: 聚合 + Repository + Domain Event
Level 3: Event Sourcing + CQRS（仅高审计需求）
```

**建议：** 至少做到 Level 1；核心业务做到 Level 2。

## 8. DDD 与架构的关系

```
DDD 战略设计                架构风格
─────────────────────────────────────────
1 个限界上下文        →     模块化单体
2–5 个上下文          →     模块化单体 / 少量服务
5+ 个上下文 + 多团队  →     微服务（每上下文一服务）
上下文间异步协作      →     事件驱动
读写差异大            →     CQRS
```

**关键：** DDD 不预设微服务；**先划分上下文，再决定部署方式**。
