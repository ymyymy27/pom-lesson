# 第4课：DDD 战略设计

> 前置：[`01-第1课限界上下文与上下文地图.md`](01-第1课限界上下文与上下文地图.md)、[`02-第2课聚合实体与值对象.md`](02-第2课聚合实体与值对象.md)

## 1. 战术 vs 战略

| 维度 | 战术设计 | 战略设计 |
|------|----------|----------|
| 关注点 | 聚合、实体、值对象 | 上下文边界、团队协作 |
| 粒度 | 单个限界上下文内 | 跨上下文、组织级 |
| 产出 | 聚合设计、Repository | 上下文地图、子域划分 |

---

## 2. 子域划分

```
核心域（Core Domain）    — 竞争优势，投入最多
支撑域（Supporting）    — 必需但非差异化
通用域（Generic）       — 可购买/外包（如邮件、支付）
```

### TaskFlow 示例子域

| 子域 | 类型 | 说明 |
|------|------|------|
| 任务协作 | 核心域 | Kanban、状态流转、分配 |
| 权限管理 | 支撑域 | RBAC，重要但非差异化 |
| 通知 | 支撑域 | 邮件/推送 |
| 身份认证 | 通用域 | OAuth/JWT，可用 Auth0 |

**原则：** 核心域自研精耕；通用域买 SaaS；支撑域适度投入。

## 3. 上下文映射（Context Map）

上下文之间的关系类型：

| 关系 | 含义 | TaskFlow 示例 |
|------|------|---------------|
| Partnership | 两个团队共同成功/失败 | Task ↔ Notification |
| Customer-Supplier | 下游依赖上游 SLA | Task → Identity（用户服务） |
| Conformist | 下游完全服从上游模型 | Reporting → Task（只读复制） |
| Anti-Corruption Layer | 翻译层隔离外部模型 | Task → Slack 集成 |
| Shared Kernel | 共享一小部分模型 | User ID 在所有上下文 |
| Open Host Service | 标准化 API 供多个消费者 | Public API |
| Published Language | 共享文档/Schema | OpenAPI Event Schema |

```
┌─────────────┐  Customer-Supplier  ┌─────────────┐
│  Identity   │ ─────────────────→ │    Task     │
│  Context    │                    │   Context   │
└─────────────┘                    └──────┬──────┘
                                        │ Partnership
                                        ↓
                                 ┌─────────────┐
                                 │ Notification│
                                 │   Context   │
                                 └─────────────┘
```

## 4. 演进策略

### 从单体到上下文

```
阶段 1：模块化单体 — 包/目录按上下文划分
阶段 2：数据库分离 — 同进程，不同 schema
阶段 3：服务拆分 — 独立部署，事件通信
```

**不要过早拆分：** 先在同一仓库内用模块边界验证，再拆微服务。

### 事件驱动集成

```python
# Task 上下文发布领域事件
class TaskAssigned(DomainEvent):
    task_id: str
    assignee_id: str
    project_id: str

# Notification 上下文订阅（通过消息队列）
@event_handler(TaskAssigned)
def notify_assignee(event: TaskAssigned):
    send_notification(event.assignee_id, f"新任务: {event.task_id}")
```
