# 第7课：远程开发协作实战 —— 多地点联调工作流

## 1. 目标：让"异地协作"像"同办公室"一样顺畅

本课把前六课的知识串成一套可落地的团队工作流。

```text
上海 同事 A 电脑               深圳 同事 B 电脑
   │  代码/本地服务                │  代码/本地服务
   │                              │
   └──────┬───────────────────────┘
          │  方式：Tailscale 虚拟内网 / SSH 隧道 / 穿透工具
          ▼
     公网云服务器（跳板机 / frp / 开发环境）
          │
          ▼
     团队共享资源：Git 仓库、数据库、测试环境、CI
```

核心原则只有三条：

1. **代码走 Git，环境走文档/脚本，数据走服务**；
2. **网络按需打通，能不开公网就不开公网**；
3. **每个环境可复现、可销毁、可远程访问**。

---

## 2. 团队网络架构：推荐模式

### 模式一：团队 Mesh 内网（最推荐）

一台云服务器作为 Tailscale 子网路由器，所有成员加入同一网络。

```text
成员电脑 ──Tailscale──> 云服务器(子网路由) ──> 开发网 10.20.0.0/16
```

优点：成员互访像内网、数据库不用暴露公网、配置一次长期有效。

### 模式二：跳板机 + SSH 隧道

只有一台公网服务器，成员按需建隧道。

优点：零额外软件；缺点：隧道需要手动维护，适合小团队。

### 模式三：穿透发布

把特定服务（Web 页面、Webhook）临时发布到公网。

优点：外部协作者无需装任何东西；缺点：不适合数据库等敏感服务。

> **混合使用**：日常互访走模式一，给外部协作者演示走模式三。

## 3. 远程开发：VS Code Remote-SSH

与其把代码拉到各自电脑跑，不如连到**统一的开发机**。

```bash
# 在本地安装 Remote-SSH 插件后
# Ctrl+Shift+P → Remote-SSH: Connect to Host → 选择你的 Host
```

### 3.1 推荐开发机配置

```text
一台云服务器（或公司内网机器）：
  - 装好 Docker（开发环境用容器跑）
  - 固定开发账号 + SSH 密钥
  - 统一 Python/Node/数据库版本（用 Docker Compose 保证一致）
  - 端口规范：8000 应用、5432 数据库、6379 Redis
```

### 3.2 为什么统一开发机

| 问题 | 统一开发机后的效果 |
|------|--------------------|
| "我这边能跑啊" | 大家跑同一个环境，复现即真相 |
| 本地配置各不同 | 环境由 Docker/脚本定义，随仓库走 |
| 数据库被各自改乱 | 数据库集中管理，可备份可重置 |
| 跨网段访问麻烦 | 大家连同一台机器，只需一次打通 |

## 4. 数据库与共享服务

### 4.1 数据库：永远走内网/隧道

不要直接把数据库暴露到公网。两种安全方式：

方式 A（Mesh VPN 内）：

```bash
psql -h 10.66.66.2 -p 5432 -U dev
```

方式 B（SSH 隧道）：

```bash
ssh -L 5432:db.internal:5432 user@jump
psql -h 127.0.0.1 -p 5432 -U dev
```

### 4.2 共享中间件

Redis、RabbitMQ、MinIO 等中间件同样只在内网开放，团队成员通过
Mesh VPN 或隧道访问。

## 5. 环境配置：.env 与规范

### 5.1 每个环境一套配置，代码里零敏感信息

```text
.env.example    # 模板，提交到仓库
.env.dev        # 开发环境（不提交）
.env.staging    # 预发布（由服务器管理员维护）
.env.prod       # 生产（只存在于生产服务器）
```

```dotenv
# .env.example
APP_PORT=8000
DATABASE_URL=postgres://app:change-me@127.0.0.1:5432/app
REDIS_URL=redis://127.0.0.1:6379/0
PUBLIC_BASE_URL=http://localhost:8000
```

### 5.2 团队约定

- 地址一律用**域名/变量**，不用写死 IP；
- 数据库连接走隧道时，本地用 `127.0.0.1`，服务器用内网地址；
- `.env` 不入库，`.env.example` 必须和实际字段同步；
- 端口统一：应用 `8000`、前端 `3000`、数据库 `5432`，避免"你 8001 我 8002"。

## 6. 联调场景实战

### 场景 1：同事访问你的本地页面

```bash
# 方式一（Tailscale）：直接访问你的 Tailscale IP
curl http://同事的TailscaleIP:3000

# 方式二（临时穿透）：
ngrok http 3000
# 把 https://xxxx.ngrok-free.app 发给同事
```

### 场景 2：钉钉/微信 Webhook 回调

```bash
ngrok http 8000
# 在钉钉开发者后台的回调地址填生成的 HTTPS URL
```

注意：

- 回调地址必须公网可达且是 HTTPS；
- 本地代码要对请求做签名校验（钉钉/微信都有文档）；
- 调试完删除回调配置，避免无效请求。

### 场景 3：A 地服务调用 B 地服务

```text
上海的服务 (svc-order) ──> Tailscale ──> 深圳的服务 (svc-payment)
```

双方配置里使用 Tailscale IP 或 MagicDNS 名称，例如：

```dotenv
PAYMENT_SERVICE_URL=http://svc-payment:8000
```

### 场景 4：共同调试一个数据库

1. 团队连上 Mesh VPN 或建好隧道；
2. 数据库只监听内网；
3. 每个成员用自己的账号连接，开发库加 `dev_` 前缀隔离数据；
4. 需要重置时由维护者执行迁移脚本，而不是手工删表。

## 7. 联调故障快速定位（实战版）

出现"连不上"时，按顺序问五个问题：

```text
1. 网络通吗？      ping / tailscale status
2. 端口通吗？      Test-NetConnection IP -Port 8000
3. 服务起来了吗？  docker ps / netstat -ano | findstr :8000
4. 配置对吗？      用的 IP/域名/端口和对方实际监听一致吗？
5. 鉴权过了吗？    token、账号、ACL 是否允许？
```

90% 的联调问题出在 **第 4 步**：地址写错、端口不一致、环境变量过期。

## 8. 团队落地清单

新成员加入协作网络时，按此清单执行：

```text
□ 生成 SSH 密钥，公钥交给管理员
□ 安装 Tailscale，加入团队网络（或配置 SSH 隧道）
□ 克隆仓库，复制 .env.example → .env.dev，填写自己的值
□ 启动本地服务，访问健康检查接口确认
□ 用 tailscale status / ssh 验证能访问共享数据库和开发机
□ 了解端口规范和环境命名（dev/staging/prod）
□ 在团队文档登记：设备名、Tailscale IP、负责服务
```

## 9. 动手练习（小组任务）

两人一组，分别位于**不同网络**（一人用手机热点也算）。

1. 双方加入同一 Tailscale 网络；
2. A 启动 `python -m http.server 3000`，B 通过 Tailscale IP 访问；
3. B 写一个简单的 FastAPI 服务（`GET /health`），A 通过 MagicDNS 调用；
4. A 把本地服务用 ngrok/Cloudflare 临时穿透，B 用手机流量访问公网 URL；
5. 配置 `.env.example`，约定双方都用 `APP_PORT=8000`；
6. 完成后在团队文档里写一份《联调环境说明》：拓扑、地址、端口、连接方式。

---

## 10. 小结

| 要点 | 做法 |
|------|------|
| 组网 | Mesh VPN 优先，隧道次之，穿透兜底 |
| 环境 | 代码随 Git，环境随脚本/Docker |
| 数据库 | 只走内网/隧道，绝不公网直连 |
| 配置 | `.env.example` 模板 + 团队规范 |
| 调试 | 按"网络→端口→服务→配置→鉴权"五步定位 |
| 文档 | 拓扑、端口、地址写进团队文档 |

**网络打通只是起点，真正的协作效率来自统一的环境、端口和配置规范。**
