# 第 03 课：实体与关系抽取

## 1. 核心问题

建图的第一步是把非结构化文本变成结构化三元组。
这一课讲清楚：有哪些抽取路线、LLM 抽取怎么做才稳定、
质量怎么把关、成本怎么控制。

## 2. 抽取任务分解

| 子任务 | 英文 | 做什么 |
|--------|------|--------|
| 命名实体识别 | NER | 找出人名、组织、项目、地点等 |
| 关系抽取 | RE | 判断实体对之间是什么关系 |
| 指代消解 | Coreference | "他"指谁、"该公司"指哪家 |
| 实体消歧 | Entity Linking | 把提及映射到规范实体 |
| 归一化 | Normalization | 别名、大小写、格式统一 |

## 3. 三条技术路线

### 3.1 规则 + NLP 管线

用正则、词表、依存句法（spaCy / LTP / HanLP）抽取。

- 优点：快、便宜、确定性强
- 缺点：泛化差，新句式要写新规则
- 适用：句式高度统一的日志、表单、固定模板文档

### 3.2 专用抽取模型

训练/微调 NER 和 RE 模型（如 GLiNER、UIE、通用 NER 模型）。

- 优点：比规则泛化好，比 LLM 便宜快
- 缺点：开放域关系类型难以枚举
- 适用：实体类型固定、关系类型少、吞吐量大的场景

### 3.3 LLM 抽取（当前主流）

把文本和 Schema 一起给 LLM，让它输出 JSON 三元组。

- 优点：理解力强、无需标注数据、Schema 可控
- 缺点：慢、贵、有幻觉（编造实体/关系）、输出不稳定
- 适用：绝大多数 GraphRAG 项目

## 4. LLM 抽取的 Prompt 设计

### 4.1 一定要给 Schema

不给 Schema 的抽取会得到"噪音图"：关系类型发散、实体五花八门。

```text
你是知识图谱构建器。从文本中抽取实体和关系。

节点类型（只能使用这些）：
- Person: 人员
- Department: 部门
- Project: 项目
- Technology: 技术

关系类型（只能使用这些）：
- REPORTS_TO: Person -> Person
- MANAGES: Person -> Department
- OWNS: Department -> Project
- WORKS_ON: Person -> Project
- USES: Project -> Technology

输出 JSON：
{"entities": [{"id": "...", "type": "...", "name": "..."}],
 "relations": [{"source": "...", "target": "...", "type": "..."}]}

只输出 JSON，不要解释。

文本：
{text}
```

### 4.2 稳定输出的技巧

1. **JSON Schema 约束**：用 Instructor / Outlines / Ollama `format: json`
   强制 JSON 格式，避免解析失败。
2. **Few-shot**：给 1~2 个例子，尤其针对难抽取的关系。
3. **逐文档抽取**：一次抽一篇/一块，避免超长文本导致遗漏。
4. **id 必须可合并**：让模型用规范名做 id（"张三"），不要用随机序号，
   否则跨文档无法合并。
5. **描述字段**：给实体/关系加 `description`，后续社区摘要和检索都靠它。

### 4.3 一个可用的抽取函数

```python
import json
import httpx

OLLAMA_URL = "http://localhost:11434"

EXTRACT_PROMPT = """...（上面的完整 Prompt）..."""

def extract_triples(text: str, model: str = "qwen2.5:7b") -> dict:
    resp = httpx.post(
        f"{OLLAMA_URL}/api/chat",
        json={
            "model": model,
            "messages": [{"role": "user", "content": EXTRACT_PROMPT.format(text=text)}],
            "stream": False,
            "format": "json",          # Ollama 强制 JSON 输出
            "options": {"temperature": 0.0, "num_predict": 500},
        },
        timeout=180.0,
    )
    content = resp.json()["message"]["content"]
    return json.loads(content)
```

## 5. 抽取质量把关

### 5.1 常见错误

| 错误 | 例子 | 后果 |
|------|------|------|
| 实体幻觉 | 文本没提"王五"，却抽出王五 | 假事实进图 |
| 关系幻觉 | "张三开发项目X"原文是"张三参与了" | 语义过强 |
| 指代错误 | 把"他"错误解析成别人 | 关系错连 |
| 类型错误 | 把"Python"标成 Person | 图结构混乱 |

### 5.2 缓解手段

- **低温**：`temperature=0`，必要时多次抽取投票
- **置信度字段**：让模型对每个三元组给 0~1 置信度，低置信度人工复核
- **来源溯源**：每条边记录 `source_doc`、`chunk_id`，可追溯
- **抽样审计**：每批抽取抽 5%~10% 人工检查，统计准确率
- **Schema 校验**：程序化校验节点/关系类型是否合法，非法丢弃

## 6. 成本控制

抽取是 GraphRAG 索引阶段最大的 token 消耗点。

| 手段 | 效果 |
|------|------|
| 缩小输入 | 只抽关键段落，不抽全文 |
| 复用缓存 | 同一文档不重复抽取（内容哈希缓存） |
| 分级模型 | 简单文档用 7B/小模型，复杂文档用大模型 |
| 批量合并 | 相关文档合并抽一次，减少重复实体 |
| 只建必要边 | Schema 收紧 = 输出 token 减少 |

经验值：1 万字文档用 7B 本地模型抽取，约产生 2k~8k 输出 token，
耗时几十秒到几分钟不等（取决于硬件）。

## 7. 抽取后的处理

抽取完不是直接入库，还要：

1. 实体归一化（别名 → 规范名）
2. 实体合并（同 id 合并描述、累加来源）
3. 关系去重（同 source-target-type 合并，count +1）
4. 悬空边处理（目标实体不存在则丢弃或挂占位节点）
5. Schema 校验与入库
