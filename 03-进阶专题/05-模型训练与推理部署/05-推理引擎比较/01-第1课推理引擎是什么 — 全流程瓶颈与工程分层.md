# 第1课：推理引擎是什么 — 全流程、瓶颈与工程分层

> 上一课：[`00-推理引擎术语表与选型速查.md`](00-推理引擎术语表与选型速查.md) · 下一课：[`02-第2课六大核心优化 — KV Cache批处理前缀缓存投机解码与量化.md`](<02-第2课六大核心优化 — KV Cache批处理前缀缓存投机解码与量化.md>)

---

## 1. 一句话理解

**推理引擎 = 把「会前向传播的模型」变成「能扛并发的在线服务」的软件层。**

它负责三件事：

1. **显存管理**：KV Cache 怎么存、怎么复用、怎么省
2. **调度批处理**：谁先算、多少人一起算、长请求怎么插队
3. **服务接口**：OpenAI 兼容 API、流式输出、量化/多卡配置

### 类比

| 日常概念 | 推理引擎 |
|---------|---------|
| 餐厅厨房 | 引擎：决定几个灶台、先做谁的菜、能不能拼桌 |
| 菜单 | 模型权重（只读，不改） |
| 外卖平台 | Serving 网关：接单、排队、超时、重试 |

---

## 2. 引擎、框架、服务的分层

| 层次 | 例子 | 职责 |
|------|------|------|
| 模型框架 | PyTorch / Transformers | 定义模型结构、前向计算、训练 |
| 推理引擎 | vLLM / SGLang / TensorRT-LLM / llama.cpp | 显存、调度、批处理、算子优化 |
| 服务层 | OpenAI API / FastAPI 网关 / Ollama | 协议、鉴权、限流、监控 |
| 部署层 | Docker / Kubernetes / GPU 调度 | 资源编排、弹性、高可用 |

> HuggingFace `model.generate()` 只能算「玩具服务」：它不做动态批处理，100 并发时显存与 GPU 利用率都会崩。生产环境必须引入推理引擎。

---

## 3. 一次推理请求的全流程

```
客户端 ──> 网关（鉴权/限流） ──> 推理引擎
                                  │
                         ┌────────▼────────┐
                         │ 调度器（排队）    │
                         └────────┬────────┘
                                  ▼
                        ┌─────────────────┐
                        │ Prefill（计算密集）│  ← TTFT
                        └────────┬────────┘
                                 ▼
                        ┌─────────────────┐
                        │ Decode（带宽密集）│  ← TPOT / ITL
                        └────────┬────────┘
                                 ▼
                              流式返回 token
```

### 两个阶段的关键差异

| 阶段 | 计算特征 | 瓶颈 | 优化方向 |
|------|---------|------|---------|
| Prefill | 输入 token 可并行 | GPU 算力 | Chunked Prefill、并行 prefill 节点 |
| Decode | 每步 1 个 token | 显存带宽 | 连续批处理、投机解码、量化 |

**TTFT 由 Prefill 主导，TPOT 由 Decode 主导。** 调优前先定位是哪个阶段慢。

---

## 4. 推理引擎解决的三大瓶颈

### 4.1 显存碎片与浪费

传统实现为每个请求预分配「最大长度」的连续显存，短请求也占满整块：

```
请求 A：实际 500 tokens，预分配 4096 → 浪费 ~88%
请求 B：实际 800 tokens，预分配 4096 → 浪费 ~80%
→ 显存利用率低，batch 上不去，吞吐上不去
```

→ 第 2 课：分页 KV Cache（PagedAttention / RadixAttention）

### 4.2 静态批处理空等

```
批次 [A, B, C, D] 一起启动
A 只要 100 tokens，B 要 2000 tokens
→ A 完成 2 秒后仍在等 B，GPU 空转
```

→ 第 2 课：连续批处理

### 4.3 框架开销

Python GIL、内核启动、显存拷贝、重复计算相同前缀。引擎通过 CUDA Graph、融合 kernel、前缀缓存把 overhead 压下去。

## 5. 引擎生态全景（2026 视角）

```
GPU 生产服务：
  ├─ vLLM       通用默认选择，生态最大
  ├─ SGLang     RadixAttention + 结构化输出 + Agent 控制流
  └─ TensorRT-LLM  NVIDIA 极致优化（NIM / 边缘盒子）

GPU 轻量 / 私有化：
  └─ LMDeploy   InternLM 系、国产芯片适配

CPU / 本地 / 边缘：
  ├─ llama.cpp + GGUF
  └─ Ollama（llama.cpp 的用户友好封装）

HF 生态：
  └─ TGI（Rust 实现，中等并发）
```

选型时问自己 4 个问题：

1. 有没有 GPU？有多少显存？
2. 并发多高、延迟要求多严？
3. 请求是不是前缀高度复用（RAG、Agent、多轮）？
4. 要不要结构化输出、思考模型、多模态？
