## 1. 先定义指标

### 延迟指标

| 指标 | 含义 | 关注点 |
|------|------|--------|
| TTFT | 首 token 延迟 | P50/P90/P99，用户体感 |
| TPOT | 每输出 token 平均耗时 | 平均即可，流式体验 |
| ITL | token 间延迟 | P99 抖动影响流式卡顿 |
| 总延迟 | 完整响应时间 | = TTFT + TPOT × tokens |

### 吞吐指标

| 指标 | 含义 |
|------|------|
| 吞吐（Throughput） | tokens/s（含输出与输入） |
| Goodput | 成功且未超时的有效吞吐 |
| 并发 vs 延迟曲线 | 找吞吐甜点与延迟拐点 |

**报指标必须带并发与分布**：`在 32 并发下 P50 TTFT=0.8s，P99=2.1s，总吞吐 1800 tok/s`。

---

## 2. 压测方法

### 准备

- 预热：先用代表请求跑 1–2 分钟，等 CUDA Graph/前缀缓存稳定
- 请求集：模拟真实混合（长短 prompt、长短输出）
- 并发梯度：8 / 16 / 32 / 64 / 128

### 工具

| 工具 | 用途 |
|------|------|
| vLLM `benchmark_serving.py` | vLLM 官方 serving 压测 |
| SGLang `bench_serving` / `oai_bench` | SGLang 官方压测 |
| `llmperf` | 通用 LLM serving 压测，输出分位延迟 |
| 自研脚本 | 贴合业务请求分布（见 `practice/benchmark_client.py`） |

### 一个可复现的流程

```
1. 固定模型/引擎版本、GPU、量化、上下文长度
2. 预热 60s
3. 每个并发档位跑 3 分钟，记录 TTFT/TPOT/吞吐/失败率
4. 同一并发重复 3 次取中位数
5. 结论写进部署文档，标注环境指纹
```

## 3. 参数调优地图

| 目标 | 优先调参 |
|------|----------|
| 降 TTFT | 前缀缓存、Chunked Prefill、PD 分离、更小上下文 |
| 降 TPOT | 投机解码、量化、提高并发利用率 |
| 提吞吐 | max-num-seqs、gpu-memory-utilization、批处理上限 |
| 降 OOM | max-model-len、量化、限制并发 |
| 降 P99 抖动 | 固定 max-num-seqs、限制最长输出、队列策略 |

### 调参原则

1. **一次只改一个参数**
2. 用同一压测脚本复现
3. 吞吐与延迟是 trade-off：高并发必然牺牲 P99
4. 线上参数 = 压测甜点 + 安全余量

## 4. 监控指标

推理服务一般暴露 Prometheus 指标（`/metrics`）：

| 指标 | 看什么 |
|------|--------|
| 排队请求数 | 排队 > 0 说明并发已满 |
| 正在运行的序列数 | 对比 max-num-seqs |
| TTFT/TPOT 直方图 | 分布与抖动 |
| GPU 显存利用率 | 是否逼近上限 |
| GPU 算力利用率 | prefill 是否吃满 |
| 缓存命中率 | 前缀缓存是否生效 |

> 可观测性体系的完整内容见 [`03-进阶专题/01-软件设计与架构/learn-observability`](../../02-部署与工程运维/可观测性)。

## 5. 常见错误认知

| 错误认知 | 正确理解 |
|---------|---------|
| 压测数字越高越好 | 必须同时报告并发与延迟分布 |
| QPS 高 = 引擎好 | 输出长度不同，token 吞吐才可比 |
| 调大 batch 一定更好 | 超过甜点后延迟恶化、吞吐停滞 |
| 首测结果可用 | 冷启动/未预热数据会误导 |
| 只看平均延迟 | 长尾 P99 才是用户痛点 |

```

并发：16
TTFT P50 / P99：___ / ___
TPOT P50 / P99：___ / ___
总吞吐：___ tok/s
失败率：___%
```

3. 尝试只改一个参数（如 max-num-seqs 翻倍），记录变化并解释
