# 第8课：权限中台设计：从业务代码到统一权限服务

## 1. 一句话解释

权限中台把分散在各业务系统的"注册权限点、判断权限、记录审计"收敛成统一服务，让业务系统只关心"调一个接口问一下"。

## 2. 类比

物业中心：各楼层（业务系统）不需要自己发门禁卡，统一到物业（权限中台）办卡、查权限、查刷卡记录。

## 3. 中台边界

中台做：

- 权限点注册与元数据管理
- 角色、策略管理（RBAC/ABAC）
- 鉴权查询（支持批量）
- 审计汇聚

中台不做：

- 业务数据存储
- 业务流程
- 前端 UI

## 4. 架构

```
业务服务 → 网关/中间件 → 权限中台（策略引擎 + 权限存储 + 审计）
              ↓
         本地权限缓存（定期同步 / 版本号失效）
```

两种集成方式：

| 方式 | 优点 | 缺点 |
|------|------|------|
| 中心化查询 | 简单、权限实时一致 | 每次请求多一次 RPC，延迟高 |
| 边车/本地缓存 | 快、可离线 | 一致性复杂，需要版本号失效 |

## 5. API 设计

```
POST /permissions                         注册权限点
GET  /roles?tenant_id=                    角色列表
POST /roles/{id}/permissions              绑定权限
POST /check                               批量鉴权
     {"user_id":"u1","tenant_id":"t1","actions":["task:read","task:delete"]}
GET  /users/{id}/effective-permissions    有效权限（含角色继承）
```

原则：鉴权接口必须支持批量（一次返回多个 action 结果），否则权限查询会成为性能瓶颈。

## 6. 缓存与失效

- 缓存键：`tenant:{tid}:user:{uid}:roles` + 权限版本号
- 权限变更 → bump 租户版本号 → 业务服务下次请求发现版本过期 → 重新拉取
- 默认 TTL + 主动失效双保险
- 敏感操作（删除、大额转账）建议实时查库或走策略引擎，不依赖缓存

## 7. 微服务集成

- JWT claims 只放用户身份与租户，**不放全部权限**（权限会变，token 里的旧权限难撤销）
- 服务间调用使用内部凭证（OAuth2 client credentials / mTLS / SPIFFE）
- 内部接口不能默认"内网即信任"
