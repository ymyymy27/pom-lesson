## 2. 高频面试题 + 参考回答

### 第一类：AI 技术认知

#### Q1: "AI产品经理和传统产品经理有什么区别？"

```
参考回答框架（3个维度）：

1. 协作对象不同
   传统PM：和设计师、前后端开发、测试协作
   AI PM：额外需要和算法工程师、数据标注团队协作
   → 需要能理解模型指标，和算法团队"说同一种语言"

2. 产品设计思维不同
   传统PM：确定性产品，功能要么有要么没有
   AI PM：概率性产品，模型效果不是100%确定
   → 需要设计兜底方案、管理用户对AI不确定性的预期

3. 项目特点不同
   传统产品：需求→开发→测试→上线，流程清晰
   AI产品：需要数据准备、模型训练、效果评估等额外环节
   → 项目不确定性更高，需要更灵活的迭代方式

总结：AI PM = 传统PM基础 + AI技术认知 + 数据思维
```

#### Q2: "大模型有什么局限性？产品上如何应对？"

```
参考回答：

5大局限性 + 对应解决方案：

1. 幻觉（最重要）
   问题：编造不存在的事实
   方案：RAG检索增强 + 引用来源 + 免责声明

2. 知识时效性
   问题：训练数据有截止时间，不知道最新信息
   方案：联网搜索 + RAG实时知识库

3. 推理能力有限
   问题：复杂数学计算和逻辑推理容易出错
   方案：工具调用（让AI调用计算器/代码执行器）

4. 缺乏私有知识
   问题：不知道企业内部数据
   方案：RAG + Fine-tuning

5. 不确定性
   问题：同样的问题可能给不同答案
   方案：降低Temperature + 设计重新生成功能 + 人工审核

产品设计原则：
  "让AI做它擅长的，用工具补它不足的，用人兜底它做不好的"
```

#### Q3: "什么是RAG？什么场景需要用？"

```
参考回答：

RAG = Retrieval-Augmented Generation（检索增强生成）

一句话解释：
  先从知识库中检索相关信息，再让大模型基于检索结果生成回答

流程：用户提问 → 检索知识库 → 找到相关文档 → 构建Prompt → LLM生成

需要RAG的场景：
  · 企业内部知识问答（公司制度、产品文档）
  · 需要准确引用来源的场景（法律、医疗）
  · 数据经常更新的场景（新闻、股价）
  · 需要减少幻觉的场景

不需要RAG的场景：
  · 通用知识问答（大模型本身就知道）
  · 创意生成（写故事、头脑风暴）
  · 知识量很小（直接写在Prompt里即可）

RAG vs Fine-tuning：
  RAG：适合知识经常更新、需要引用来源
  Fine-tuning：适合改变模型行为/风格、知识相对固定
  实际中经常两者结合使用
```

#### Q4: "如何评估一个AI模型的效果？"

```
参考回答：

分两种情况：

1. 传统ML模型（分类/回归）
   · 分类：Precision/Recall/F1/AUC
   · 回归：MSE/RMSE/R²
   · 关键：指标选择取决于业务场景中FP和FN的代价

2. 大模型/生成式AI
   · 自动评估：BLEU/ROUGE（文本相似度）
   · 模型互评：用GPT-4评估其他模型
   · 人工评估：准确性/相关性/安全性/流畅性多维度打分
   · 用户反馈：👍👎满意度

   上线标准示例：
     "评估集整体满意率 > 85%"
     "幻觉率 < 5%"
     "安全问题检出率 < 0.1%"
     "首字延迟 < 2秒"

我的观点：
  不能只看单一指标，要建立多维度评估体系
  最终要和业务目标对齐——模型指标提升是否带来了业务指标提升
```

### 第二类：产品设计

#### Q5: "设计一个XX场景的AI产品"（产品设计题）

```
回答框架（5步法）：

以"设计一个AI智能客服"为例：

Step 1: 明确场景和用户
  目标用户：电商平台的购物用户
  核心场景：售前咨询、售后问题、物流查询
  用户痛点：等待时间长、问题重复、人工成本高

Step 2: 定义核心功能
  P0（必须有）：
    · 意图识别：理解用户问题类型
    · 知识库问答：基于FAQ和产品知识回答
    · 订单查询：对接订单系统查询物流/退款状态
    · 转人工：复杂问题无缝转接人工
  
  P1（重要）：
    · 多轮对话：记住上下文
    · 情绪识别：检测用户不满，主动升级
  
  P2（可以后做）：
    · 主动推荐：根据用户浏览推荐商品
    · 多语言支持

Step 3: 技术方案选型
  · 意图识别：LLM 分类
  · 知识库问答：RAG（FAQ + 产品文档）
  · 订单查询：Agent（工具调用订单API）
  · 转人工：规则触发（关键词+情绪+多次失败）

Step 4: 关键交互设计
  · 开场白引导："您好，我是AI客服，可以帮您..."
  · AI不确定时："我可能没完全理解您的问题，要不我帮您转接人工？"
  · 引用来源："根据我们的退款政策..."

Step 5: 衡量指标
  · 解决率：AI独立解决问题的比例（目标>70%）
  · 转人工率：目标<30%
  · 用户满意度：目标>4.0/5.0
  · 响应时间：<3秒
  · 人力成本节省：目标>50%
```

#### Q6: "你最近深度体验了哪个AI产品？怎么评价？"

```
回答框架：

以 Kimi 为例：

1. 产品定位
   Moonshot AI 出品的AI对话助手
   核心差异化：超长文本处理（200万字上下文）

2. 核心功能分析
   ✅ 长文档理解：上传PDF/长文本，总结和问答效果好
   ✅ 联网搜索：回答包含最新信息
   ✅ 中文优化：中文理解和表达质量高

   ❌ 生态封闭，无插件系统

3. 用户体验
   优点：界面简洁、新用户引导好、回答质量稳定
   不足：长文档处理等待时间较长、没有语音交互

4. 我的建议（展示PM思维）
   · 可以增加"快捷操作"（一键总结/翻译/改写）
   · 长文档处理可以加进度条和分段预览
   · 可以开放API/插件生态吸引开发者

准备3个产品的深度体验，面试时轮换使用
```

### 第三类：行业认知

#### Q7: "你怎么看当前AI行业的发展趋势？"

```
参考回答框架：

1. 技术趋势
   · 大模型能力持续提升（推理、多模态）
   · 小模型/端侧模型兴起（成本低、隐私好）
   · Agent 从概念走向落地
   · 多模态成为标配

2. 应用趋势
   · 从"对话"到"执行"（Agent 帮你做事，不只是聊天）
   · 从"通用"到"垂直"（医疗AI、法律AI、教育AI）
   · AI 融入现有工作流（Office+AI、IDE+AI）

3. 商业趋势
   · API 调用成本持续下降
   · 订阅制成为主流商业模式
   · 企业级市场（B端）是主要变现方向

4. 我的判断（展示独立思考）
   "我认为短期内 RAG+Agent 是最容易落地的方向，
    因为它直接解决企业的知识管理和流程自动化需求，
    商业价值清晰，技术栈也相对成熟。"
```

#### Q8: "如果让你做一个AI产品创业，你会选什么方向？"

```
回答思路：展示你对市场的理解和商业判断

示例：
  方向：面向中小企业的AI智能客服SaaS

  为什么选这个：
  1. 市场大：中国有几千万家中小企业，客服需求普遍
  2. 痛点明确：人工客服贵、响应慢、质量不稳定
  3. 技术成熟：RAG+LLM 已经能很好地处理FAQ类问答
  4. 商业模式清晰：SaaS订阅，按坐席/对话量收费
  5. 差异化：专注中小企业（简单易用），而非大厂的复杂方案

  怎么做：
  · MVP：支持上传FAQ文档→自动生成AI客服→嵌入网站
  · 核心指标：解决率>60%（降低人工成本）
  · 获客：从电商/教育等高频客服行业切入
```

### 第四类：数据分析 & SQL

#### Q9: "用SQL查询过去7天每日活跃用户数"

```sql
SELECT
    login_date,
    COUNT(DISTINCT user_id) AS DAU
FROM user_logins
WHERE login_date >= CURRENT_DATE - INTERVAL 7 DAY
GROUP BY login_date
ORDER BY login_date;
```

#### Q10: "计算次日留存率"

```sql
SELECT
    DATE(u.created_at) AS reg_date,
    COUNT(DISTINCT u.id) AS reg_count,
    COUNT(DISTINCT l.user_id) AS retain_count,
    ROUND(COUNT(DISTINCT l.user_id) * 100.0
        / COUNT(DISTINCT u.id), 1) AS retention_rate
FROM users u
LEFT JOIN user_logins l
    ON u.id = l.user_id
    AND l.login_date = DATE(u.created_at) + INTERVAL 1 DAY
WHERE u.created_at >= '2024-01-01'
GROUP BY DATE(u.created_at)
ORDER BY reg_date;
```
