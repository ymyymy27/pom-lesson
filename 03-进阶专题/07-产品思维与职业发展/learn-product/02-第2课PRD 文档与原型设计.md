# 第2课：PRD 文档与原型设计

## 1. PRD 是什么？

### 一句话定义
**PRD (Product Requirements Document) 是产品经理最核心的输出物** —— 它把"我们要做什么"翻译成开发团队能理解和执行的文档。

### PRD 的作用

```
产品经理的想法 → PRD → 设计师/开发/测试 → 产品上线

PRD 回答三个问题：
  1. 做什么？（功能描述）
  2. 为什么做？（背景和目标）
  3. 做成什么样？（详细规则和原型）
```

### PRD vs 其他文档

| 文档 | 面向对象 | 内容 | 详细程度 |
|------|---------|------|---------|
| BRD (商业需求) | 老板/投资人 | 为什么值得做、商业价值 | 宏观 |
| MRD (市场需求) | 市场/运营 | 目标用户、市场分析 | 中等 |
| **PRD (产品需求)** | **设计/开发/测试** | **功能细节、交互规则** | **详细** |

## 2. PRD 模板

### 完整模板结构

```markdown
# [产品/功能名称] PRD

## 1. 修订记录
| 版本 | 日期 | 修改人 | 修改内容 |
|------|------|--------|---------|
| v1.0 | 2024-01-15 | 张三 | 初版 |
| v1.1 | 2024-01-20 | 张三 | 增加异常流程 |

## 2. 背景与目标
### 2.1 背景
  - 当前问题是什么？
  - 用户反馈/数据支撑？

### 2.2 目标
  - 核心指标：XX 提升 XX%
  - 预期上线时间：2024-XX-XX

### 2.3 不包含在本期的内容（Out of Scope）
  - 明确告诉团队这次不做什么

## 3. 用户故事
  作为一个 [角色]，我想要 [功能]，以便 [价值]。

## 4. 功能详细设计

### 4.1 功能概览（信息架构图）

### 4.2 功能点 1：[名称]
  - 入口：从哪里进入
  - 交互流程：用户操作步骤
  - 页面描述：每个页面的元素和布局
  - 业务规则：
    - 规则1：XXX
    - 规则2：XXX
  - 异常处理：
    - 网络异常 → 提示"网络不佳，请重试"
    - 数据为空 → 显示空状态页

### 4.3 功能点 2：[名称]
  （同上结构）

## 5. 数据埋点需求
| 事件名 | 触发时机 | 参数 | 目的 |
|--------|---------|------|------|
| page_view | 进入页面 | page_name | 统计PV |
| btn_click | 点击按钮 | btn_name | 转化分析 |

## 6. 非功能需求
  - 性能：页面加载 < 2秒
  - 兼容性：iOS 14+, Android 10+
  - 安全：敏感信息脱敏

## 7. 原型/设计稿
  （附 Figma/墨刀链接）

## 8. 上线计划
  - 灰度策略
  - 回滚方案
  - 数据监控
```

## 3. PRD 写作技巧

### 3.1 写清楚业务规则

```
❌ 模糊：用户可以搜索商品
✅ 清晰：
  1. 搜索框位于首页顶部，支持输入关键词搜索
  2. 输入 ≥ 1 个字符时开始联想推荐
  3. 联想结果最多展示 8 条，按搜索热度排序
  4. 点击搜索或回车后跳转搜索结果页
  5. 搜索无结果时显示"未找到相关商品"+ 热门推荐
  6. 搜索历史保留最近 20 条，可一键清除
```

### 3.2 写清楚异常流程

```
正常流程：用户操作成功的路径
异常流程（容易遗漏！）：
  - 网络断开/超时
  - 数据为空
  - 输入不合法（特殊字符、超长文本）
  - 权限不足
  - 并发操作（两人同时编辑）
  - 系统错误 / 服务降级
```

### 3.3 交互描述要具体

```
❌ 模糊：点击后弹出提示
✅ 清晰：
  点击"删除"按钮后：
  1. 弹出确认对话框，标题"确认删除"
  2. 正文："删除后不可恢复，确定要删除吗？"
  3. 两个按钮："取消"（灰色）和"确认删除"（红色）
  4. 点击"取消"关闭对话框，不做操作
  5. 点击"确认删除"执行删除，成功后 Toast 提示"删除成功"
  6. 删除失败时 Toast 提示"删除失败，请重试"
```

## 4. 原型设计

### 4.1 什么是原型？

```
原型 = 产品的"草图" → 让团队直观理解功能和交互

低保真原型：线框图，只有布局和文字，不关注视觉
高保真原型：接近真实产品，有颜色、图标、可交互
```

### 4.2 常用原型工具

| 工具 | 特点 | 适合场景 |
|------|------|---------|
| **Figma** | 在线协作、功能强大、免费版够用 | 首推，业界标准 |
| **墨刀** | 中文友好、AI生成原型、模板多 | 快速出原型 |
| Axure | 交互逻辑强大 | 复杂交互产品 |
| 即时设计 | 国产 Figma 替代 | 国内团队 |
| 手绘草图 | 纸笔即可 | 早期头脑风暴 |

### 4.3 原型设计原则

```
1. 先画流程，再画页面
   用户路径：首页 → 搜索 → 商品详情 → 加购 → 下单 → 支付

2. 标注清楚
   每个元素的状态、交互、跳转都要标注
   默认状态 / 加载状态 / 空状态 / 错误状态

3. 保持一致性
   按钮样式、字体大小、间距在全局保持统一

4. 考虑边界情况
   文字超长怎么显示？（截断/换行/...）
   图片加载失败显示什么？（占位图）
   列表为空显示什么？（引导页）
```

### 4.4 常见页面类型

```
列表页：   展示多条信息（商品列表、聊天列表）
详情页：   单条信息的完整展示（商品详情、用户主页）
表单页：   用户输入信息（注册、下单、填写地址）
搜索页：   搜索入口 + 结果展示
设置页：   配置项集合
弹窗/浮层：轻量级交互（确认框、分享面板）
空状态页： 暂无数据时的引导
```

## 5. 需求评审

### 5.1 评审流程

```
评审前：
  1. 提前 1-2 天发出 PRD 给相关同事
  2. 邀请参会人：设计、前端、后端、测试、（运营）
  3. 准备好原型/设计稿

评审中：
  1. 5 分钟讲背景和目标
  2. 逐个功能点讲解，配合原型演示
  3. 记录所有问题和意见
  4. 当场能回答的立即回答
  5. 不能回答的记录下来，会后确认

评审后：
  1. 整理会议纪要，发给所有参会人
  2. 更新 PRD（解决提出的问题）
  3. 确认开发排期
```

### 5.2 常见评审问题

```
开发常问：
  "这个接口返回什么数据？"  → PRD 要写清楚数据字段
  "异常情况怎么处理？"      → 补充异常流程
  "这个功能排期多久？"      → 和开发协商

设计常问：
  "这个交互参考哪个产品？"  → 准备竞品截图
  "文案是这个吗？"          → 确认所有文案

测试常问：
  "边界值是什么？"          → 输入长度、数值范围
  "需要兼容哪些设备？"      → 明确兼容性要求
```

## 6. PRD 实战：AI 聊天助手

```markdown
# AI 聊天助手 v1.0 PRD

## 背景
公司内部需要一个基于大模型的知识问答助手，帮助员工快速查询公司制度和产品文档。

## 目标
- 上线后 1 个月内 DAU > 200
- 问题回答满意度 > 80%

## 功能设计

### 功能1：对话交互
- 页面底部输入框，支持文字输入
- 发送后显示用户气泡（右侧）和 AI 回复气泡（左侧）
- AI 回复支持流式输出（打字机效果）
- 支持 Markdown 格式渲染（代码块、列表、表格）

业务规则：
  - 单条消息最长 2000 字
  - 超长时提示"消息过长，请精简后重试"
  - AI 回复超时(30s)显示"回复超时，请重试"
  - 上下文保留最近 10 轮对话

### 功能2：知识库引用
- AI 回复时，如果引用了知识库文档，在回复下方显示"引用来源"
- 点击来源可跳转到原文档

### 功能3：反馈机制
- 每条 AI 回复下方有 👍 和 👎 按钮
- 点击 👎 弹出文本框，用户可填写不满意原因

## 埋点需求
| 事件 | 触发 | 参数 |
|------|------|------|
| send_message | 用户发送消息 | msg_length |
| ai_response | AI 回复完成 | response_time, has_reference |
| feedback | 用户点击反馈 | type(up/down), reason |
```

## 7. 动手练习

1. **写 PRD**：为"AI 文档总结助手"写一份完整 PRD（上传 PDF → AI 生成摘要）
2. **画原型**：用 Figma 或墨刀画出 AI 聊天助手的 3 个核心页面
   - 对话主页面
   - 历史对话列表
   - 知识库管理页
3. **需求评审**：模拟向开发同事讲解你的 PRD，预想他们会问什么问题

## 8. 小结

| 概念 | 核心要点 |
|------|---------|
| PRD | 产品经理最核心输出，写给开发/设计/测试看 |
| PRD 关键 | 业务规则要细、异常流程要全、交互描述要具体 |
| 原型 | 产品的可视化草图，Figma/墨刀为主流工具 |
| 需求评审 | PRD + 原型一起评审，记录问题并更新文档 |
