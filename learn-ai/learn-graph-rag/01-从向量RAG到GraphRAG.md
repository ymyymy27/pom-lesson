# 第 01 课：从向量 RAG 到 GraphRAG

## 1. 核心问题

向量 RAG 已经能解决"帮我找文档里关于 X 的内容"，为什么还需要图？
答案藏在两类问题上：**需要跨文档拼接关系的问题**和**需要全局视野的问题**。

## 2. 向量 RAG 的五个失效场景

### 2.1 多跳推理（Multi-hop）

问题："张三的上级管理的部门，负责什么项目？"

信息分散在三条文档里：

- 文档 A：张三汇报给李四
- 文档 B：李四管理研发部
- 文档 C：研发部负责项目 X 和项目 Y

向量检索分别找"张三""上级""部门""项目"相关文本块，最相关的块往往只含其中一环，
LLM 拿不到完整链条，只能猜。检索结果里块与块之间**没有连接关系**。

### 2.2 全局性问题（Global / 聚合）

问题："公司所有团队分别负责什么方向？"

这是"查询聚焦摘要"（Query-Focused Summarization, QFS）问题：
需要把整个语料读一遍再总结。向量 RAG 只能取 Top-K 块，天然做不了全局。

### 2.3 实体中心问题（Entity-centric）

问题："李四参与了哪些项目？他的技术栈是什么？"

答案可能分布在 50 个文档里。向量检索按"相似度"取块，容易漏掉
"李四"作为主语出现但描述很短的句子；图可以沿着"李四—参与—项目"边精确枚举。

### 2.4 别名与同指

文档里"张三""张总""Zhang San"可能指同一个人。向量检索把它们当成不同文本；
图构建时可以做实体归一化（Entity Resolution），把多个名字合并成一个节点。

### 2.5 关系型查询

"谁和谁是同事？""哪些项目共用 PostgreSQL？"这类问题的本质是**关系代数**，
相似度检索不是正确的计算模型，图遍历/图查询才是。

## 3. GraphRAG 的定义

GraphRAG = 以知识图谱为索引结构、以图算法参与检索的 RAG。

广义上分两类：

| 类型 | 检索方式 | 代表 |
|------|---------|------|
| 图检索增强（KG-RAG） | 实体链接 + 图遍历/Text2Cypher + 向量混合 | Neo4j GraphRAG、KAG |
| 社区增强（GraphRAG 原义） | 建图 → 社区检测 → 社区摘要 → 全局/局部检索 | Microsoft GraphRAG、LightRAG |

狭义上，"GraphRAG" 通常指 Microsoft 提出的方案（arXiv:2404.16130），
核心创新是**社区检测与社区摘要**，让 LLM 能做全局问答。
本课程两种都会讲，先建立统一框架：

```
文档
  │
  ├─→ 分块 + Embedding ──→ 向量索引（语义检索）
  │
  └─→ 实体/关系抽取 ──→ 知识图谱 ──→ 图检索（路径/社区/中心性）
                                      │
                                      ▼
                         向量结果 + 图结果 融合
                                      │
                                      ▼
                                   Rerank
                                      │
                                      ▼
                                  LLM 生成
```

## 4. 为什么图能让 LLM 更强

1. **可组合性**：图把知识拆成最小单元（三元组），查询时按需组合，
   而不是依赖"恰好有一个文本块包含完整答案"。
2. **可追溯性**：每个回答都能给出推理路径
   （张三 → REPORTS_TO → 李四 → MANAGES → 研发部 → OWNS → 项目X），
   这在企业场景里是审计和信任的关键。
3. **全局抽象**：社区摘要等于"自动生成目录/综述"，让 LLM 先看全局再回答细节。
4. **降低幻觉**：检索结果从"相似文本"变成"可验证的事实路径"，
   生成环节被约束在路径范围内。

## 5. GraphRAG 的代价

不要神化 GraphRAG，它有三笔显性成本：

| 成本 | 说明 |
|------|------|
| 建图成本 | 实体关系抽取要调 LLM，token 消耗远高于 Embedding |
| 存储与维护 | 图数据库/图谱要设计 Schema、处理实体消歧、增量更新 |
| 检索复杂度 | 图检索逻辑比向量检索复杂，调试和评估更难 |

所以正确的问题是"什么场景值得付这些成本"，而不是"GraphRAG 是不是更高级"。

## 6. 决策框架

```
问题需要多跳关系推理或全局总结吗？
  ├─ 否 ─→ 纯向量 RAG 足够，先别上图
  └─ 是 ─→ 实体关系是否稳定、可抽取？
              ├─ 否 ─→ 考虑 Agentic RAG（工具调用迭代检索），而不是硬建图
              └─ 是 ─→ 规模小（<100 文档）→ LightRAG / LlamaIndex PropertyGraph
                        规模大（≥1000 文档）→ Microsoft GraphRAG / KAG / 自研管道
```

## 练习与自测

1. 给出一个你见过的"纯向量 RAG 答错、图能答对"的问题。
2. 解释"全局性问题"为什么 Top-K 检索天然解决不了。
3. 判断题：GraphRAG 一定会比向量 RAG 效果更好。（答案：错，取决于场景与成本）
4. 思考：如果文档里实体混乱、重复严重，先处理图质量还是先上检索？为什么？

（第 4 题方向：先处理质量。垃圾进垃圾出，图质量差时检索再聪明也没用。）
