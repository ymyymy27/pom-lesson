# 第 02 课：知识图谱核心概念

## 1. 核心问题

图谱不是"一张会画线的图"，而是一种**带类型的事实数据库**。
这一课把节点、边、Schema、三元组、实体消歧这些概念讲透，
因为后面所有算法都建立在这些概念上。

## 2. 图的基本要素

一个属性图（Property Graph）由四部分组成：

| 要素 | 定义 | 例子 |
|------|------|------|
| 节点 Node | 一个实体，有唯一 ID 和类型 | `(张三:Person)` |
| 边 Edge | 两个节点之间的有向关系 | `(张三)-[:REPORTS_TO]->(李四)` |
| 属性 Property | 节点/边上的键值信息 | `张三 {name:"张三", title:"工程师"}` |
| 标签 Label | 节点的类型 | `Person`、`Department`、`Project` |

例子：

```text
(张三:Person {title:"工程师"})
  -[:REPORTS_TO {since:"2023"}]-> (李四:Person {title:"总监"})
  -[:MANAGES]-> (研发部:Department)
  -[:OWNS]-> (项目X:Project {stack:"Python, PostgreSQL"})
```

## 3. 三元组：图的最小知识单位

知识图谱最常见的表示是三元组：

```text
主语 (Subject) — 谓语 (Predicate) — 宾语 (Object)
张三            — REPORTS_TO       — 李四
研发部          — OWNS             — 项目X
```

三元组的好处：

- 每一条都是**可独立验证**的事实
- 可以拆开存储、索引、检索
- 天然支持合并：多条文档的相同实体自动汇聚

注意区分：

- **RDF 图**：节点和边都是全局 URI，适合开放数据交换（如 Wikidata）
- **属性图**：节点/边带属性与标签，适合应用开发（如 Neo4j）

GraphRAG 实践里绝大多数用属性图，理解属性图就够。

## 4. Schema：图的"数据库表结构"

Schema 定义允许出现的节点类型、关系类型、属性、约束。
它是抽取和检索之间的"合同"。

```yaml
# 组织知识图谱 Schema 示例
nodes:
  Person:
    properties: [name, title]
  Department:
    properties: [name]
  Project:
    properties: [name, status, stack]
relations:
  REPORTS_TO:   # 从 Person 到 Person
    source: Person
    target: Person
  MANAGES:      # 从 Person 到 Department
    source: Person
    target: Department
  OWNS:         # 从 Department 到 Project
    source: Department
    target: Project
  WORKS_ON:     # 从 Person 到 Project
    source: Person
    target: Project
```

### 4.1 Schema 为什么重要

1. **约束抽取**：LLM 只按 Schema 输出，关系类型不会失控
   （不会冒出 300 种"有关系""相关"这种噪声关系）。
2. **保证可查询**：Schema 定了，Cypher/图遍历才能写对。
3. **控制成本**：关系类型少，抽取和存储都便宜。

### 4.2 Schema 设计原则

- 节点类型 5~15 个为宜；关系类型 10~30 个为宜
- 关系名用动词/介词短语，语义明确（`REPORTS_TO` 比 `RELATED` 好）
- 能加属性的不单独建节点（"状态"是属性，不是节点）
- 高频查询决定 Schema：先列 20 个必答问题，再反推节点和边

## 5. 实体消歧（Entity Resolution）

同一实体可能有多个名称：

```text
张三 / 张总 / Zhang San / 研发部张三
```

消歧的三个层次：

| 层次 | 方法 | 适用 |
|------|------|------|
| 规范化 | 去空格、统一大小写/繁简 | 文本清洗 |
| 别名映射 | 维护 alias → canonical 词典 | 固定实体集 |
| 语义合并 | Embedding 相似度 + 规则，判定是否同一实体 | 开放域 |

消歧错误的两类代价：

- **欠合并**：同一实体两个节点，路径断裂，多跳查询漏答
- **过合并**：两个不同实体被合并，关系张冠李戴，回答出错且难排查

生产系统里，宁可**欠合并**也不要**过合并**——错误合并污染整张图。

## 6. 图的层次结构：社区

实体图天然有"抱团"结构：同一部门的人之间边多，部门之间边少。
社区（Community）就是这种稠密子图。

```
        [研发部社区]
   张三 ── 李四 ── 王五
     │     │      │
     └── 项目X ───┘
          │
   [市场部社区] ── 赵六 ── 项目Y
```

社区检测是 Microsoft GraphRAG 的基石：
社区可以理解为"自动生成的主题目录"，后面第 5 课详细展开。

## 7. 图 vs 向量：互补而非替代

| 维度 | 向量索引 | 图索引 |
|------|---------|--------|
| 基本单位 | 文本块（chunk） | 实体与关系（三元组） |
| 相似性 | 语义相似 | 结构连接 |
| 擅长 | 模糊搜索、开放问答 | 精确关系、多跳、聚合 |
| 全局性 | 差（Top-K） | 好（社区/路径） |
| 构建成本 | 低 | 高 |
| 可解释性 | 低 | 高（路径可见） |

两者的关系是互补：**向量负责"找到相关入口"，图负责"沿着关系扩展"**。
