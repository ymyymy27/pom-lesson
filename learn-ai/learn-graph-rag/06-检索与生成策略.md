# 第 06 课：检索与生成策略

## 1. 核心问题

图建好了，查询时到底怎么"用"？这一课给出可组合的检索原语：
实体链接、Text2Cypher、子图遍历、社区检索、个性化 PageRank，
以及如何融合多路结果、如何让 LLM 基于图生成回答。

## 2. 检索第一步：实体链接（Entity Linking）

把问题里的自然语言提及映射到图节点。

三种做法：

| 方法 | 说明 | 适用 |
|------|------|------|
| 词法匹配 | 精确/包含匹配 + 别名表 | 实体名规范 |
| 向量匹配 | 问题片段 Embedding 与实体描述相似度 | 同义词、口语化 |
| LLM 链接 | 让 LLM 从问题中挑实体并指定规范名 | 复杂指代 |

示例：

```python
def link_entities(question: str, graph, aliases: dict):
    mentions = []
    for alias, canonical in aliases.items():
        if alias in question:
            mentions.append(canonical)
    # 别名没命中时，用 Embedding 在实体名/描述里找 Top-K
    return mentions
```

实体链接失败的后果：图检索从根上断掉。所以生产系统要
**链接 + 兜底**：链接不到实体时降级为纯向量检索。

## 3. 检索原语

### 3.1 Text2Cypher

问题 → LLM 生成 Cypher → 执行 → 精确结果。

风险与对策：

- 生成语法错误 → 重试 1~2 次或给错误信息让 LLM 修正
- 生成语义错误（问东查西）→ 用 Schema 约束 + 示例 few-shot
- 关系方向写反 → 本课程实战中就出现过：问"张三汇报给谁"，
  模型生成 `(张三)<-[:REPORTS_TO]-(m)`，方向完全反了，执行后查不到任何结果
- 实体名被改写 → 实战中"项目X"被生成成 `'X'`，匹配不到节点；
  对策是实体名不靠模型自由发挥，改为"实体链接 + 参数注入"
- 注入风险（问题里带恶意 Cypher）→ 只读用户权限、参数化、禁止 DDL

### 3.2 子图遍历（k-hop）

```python
import networkx as nx

def subgraph_context(graph, seeds, hops=2, max_nodes=30):
    nodes = set()
    for seed in seeds:
        if seed in graph:
            nodes.update(
                nx.single_source_shortest_path_length(graph, seed, cutoff=hops)
            )
    nodes = sorted(nodes, key=lambda n: graph.degree(n), reverse=True)[:max_nodes]
    return graph.subgraph(nodes)
```

裁剪策略：限制跳数、按度排序取 Top-N、按边权重过滤。

### 3.3 社区检索（Global）

问题向量 vs 社区摘要向量 → Top-K 社区 → 读社区摘要。
适合"主题/全局"问题。

### 3.4 个性化 PageRank（PPR）

以查询实体为种子做随机游走，给全图节点打分。

```python
def ppr_scores(graph, seeds, alpha=0.85):
    personalization = {n: 1.0 for n in seeds}
    return nx.pagerank(graph, alpha=alpha, personalization=personalization)
```

特点：一次计算得到全图相关度排序，是 HippoRAG 的核心；
比 k 跳更"软"，能跨弱连接找到关联。

## 4. 多路融合（Hybrid）

真实系统通常是多路检索：

```
             ┌─ 向量检索（TextUnit）─────────┐
问题 ────────┼─ 子图遍历（k-hop）────────────┼─→ 合并 → 去重 → Rerank → LLM
             └─ 社区检索（Global）───────────┘
```

### 4.1 合并（RRF 倒数排名融合）

```python
def rrf(results: list[list], k: int = 60) -> dict:
    scores = {}
    for ranked in results:
        for rank, item in enumerate(ranked):
            scores[item] = scores.get(item, 0) + 1.0 / (k + rank)
    return scores
```

RRF 的优点：不依赖各路的分数可比较（向量相似度和图得分单位不同）。

### 4.2 重排序

融合后用 Cross-Encoder / LLM 对候选做二次排序，只留 Top-N。

## 5. 上下文组装：图怎么"讲"给 LLM

结构化的上下文模板：

```text
【实体】
- 张三 (Person): 工程师；汇报对象：李四

【关系】
- 张三 -REPORTS_TO-> 李四（来源：组织架构.md#chunk3）

【路径】
- 张三 → 李四 → 研发部 → 项目X

【原文片段】
（相关 TextUnit 原文，按需附上）
```

组装原则：

1. 先给结论性结构（节点/边/路径），再给原文
2. 路径比孤立节点更有用（路径就是推理线索）
3. 每条信息带来源，生成时强制引用
4. 控制总量：节点 ≤ 50、边 ≤ 100，超出按权重裁剪

## 6. 生成策略

### 6.1 直接生成

上下文不大时，一次生成。适合 Local 问题。

### 6.2 Map-Reduce 生成

上下文分块 → 各自生成部分答案 → 合并。适合 Global 问题。

### 6.3 Agent 循环

LLM 先决定检索什么，再基于结果决定下一步：

```
问题 → 生成检索计划 → 执行图查询 → 评估信息是否够
  → 不够 → 新一轮检索 → 够了 → 生成最终答案
```

这就是 2025~2026 年主流的 **Agentic GraphRAG** 形态。

### 6.4 生成约束

```text
规则：
1. 只使用上下文中的事实，禁止编造
2. 每个结论标注来源（节点/文档）
3. 如果上下文不足以回答，明确说"信息不足"
4. 涉及多步推理时，先展示路径再给结论
```

## 7. 一张图总结

```
问题
 ├─ 实体链接（词法/向量/LLM）
 ├─ 检索原语：Cypher / k-hop / 社区 / PPR
 ├─ 多路融合：RRF → Rerank
 ├─ 上下文组装（结构 + 来源）
 └─ 生成：直接 / Map-Reduce / Agent
```
