# 第 02 课：文本处理与中文分词

## 1. 核心问题

搜索引擎的索引和查询都必须建立在"词项"（Term）之上。
把原始文本变成词项的这一步叫**文本分析（Analysis）**，
其中中文分词是整个环节里最难的。

## 2. 文本分析管道

```
原始文本
  → 字符规范化（大小写、全半角、繁简）
  → 分词（Tokenization）
  → 过滤（停用词、标点、数字策略）
  → 归一化（词干/词形还原，或中文同义映射）
  → 词项序列
```

### 2.1 字符规范化

```text
"Hello" → "hello"
"ＦＡＳＴＡＰＩ" → "fastapi"（全角转半角）
"數據庫" → "数据库"（繁转简，视场景）
```

规范化不一致，会导致"同一个词"查不到：索引里是 `Hello`，查询是 `hello`，
倒排索引按字符串精确匹配，永远匹配不上。

### 2.2 停用词（Stopwords）

过滤"的、了、是、在"等高频无意义词。

注意：停用词表要**按领域定制**。通用停用词表把"北京"拆成"北/京"没问题，
但如果把"数据分析"里的"分析"当停用词，检索就废了。

### 2.3 词干还原（Stemming）

```text
running → run，books → book
```

中文没有形态变化，所以词干还原对中文不是刚需；
但中文有**同义词/缩写**问题（"AI""人工智能""大模型"），需要词典映射。

## 3. 中文分词为什么难

英文以空格分隔，分词几乎是免费的。中文没有天然分隔符：

```text
"研究生命起源" 可以切为 "研究生/命/起源"，也可以切为 "研究/生命/起源"
"南京市长江大桥" 可以切为 "南京市/长江大桥"，也可以切为 "南京/市长/江大桥"
```

分词歧义两大类：

- **交集型歧义**："研究生命"中"研究"与"研究生"共享字符
- **组合型歧义**："将来"既可作一个词，也可作"将/来"

分词错了，检索和排序就建立在错误的词项上。

## 4. 三种分词路线

### 4.1 词典分词（规则）

基于词典做最大匹配：

- 正向最大匹配（FMM）：从左往右尽量取最长词
- 逆向最大匹配（BMM）：从右往左，中文通常 BMM 更准

```text
词典：[南京, 南京市, 市长, 长江, 长江大桥, 江大桥, 大桥]
输入："南京市长江大桥"
FMM：南京市 / 长江大桥
BMM：南京市 / 长江大桥（本例相同，很多句子两者不同）
```

优点：快、可控；缺点：无法处理未登录词（"星辰科技"不在词典就切碎）。

### 4.2 统计分词（无监督）

用 n-gram 共现频率判断哪些字符组合更像"词"（互信息、左右熵）。

优点：能发现新词；缺点：需要大规模语料，质量不如监督方法。

### 4.3 机器学习/深度学习分词

把分词当序列标注任务（B/I/E/S 标注），用 HMM/CRF/BERT 训练。

优点：准确率高、泛化好；缺点：需要标注数据或模型服务。

### 4.4 工程实践

生产中常用**词典 + 统计 + 模型**的混合方案：

- jieba（Python）：词典 + HMM，足够学习与原型
- HanLP / LTP：更专业的中文 NLP
- Elasticsearch IK 分词器：最常用的中文 ES 方案
- 兜底策略：分词结果为空时，退回**字符 n-gram**（如二元组），保证能匹配

## 5. 字符 n-gram：分词的保险丝

很多搜索引擎（尤其是容错场景）不依赖完美分词，直接用 n-gram：

```text
"星辰科技" → 二元组：星辰 / 辰科 / 科技
```

n-gram 的优点：

- 不需要词典，任何文本都能切
- 天然抗拼写错误（"星辰科技"少一个字也能部分匹配）
- 中文场景下二元组（bigram）检索效果通常不错

缺点：索引膨胀（每个字产生 n-1 个词项）、语义粒度粗。

## 6. 索引侧与查询侧必须一致

这是搜索引擎最常见的问题：

```text
索引时：对文档做"中文分词 + 停用词过滤"
查询时：只做了小写转换，没有分词
结果：永远匹配不上
```

规则：**文档分析和查询分析必须使用同一套管道**。
实战代码里会用一个函数同时处理文档和查询，就是为了避免这个问题。
