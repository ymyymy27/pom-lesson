# 第 05 课：向量检索与混合检索

## 1. 核心问题

BM25 匹配"字面"，向量检索匹配"语义"。这一课讲清楚：
向量检索怎么工作、有哪些工程代价、以及为什么最终要两者混合。

## 2. 向量检索的基本流程

```
文档 → Embedding 模型 → 文档向量 → 存入向量索引（HNSW 等）
查询 → Embedding 模型 → 查询向量 → 最近邻搜索（ANN）
                                    → Top-K 文档
```

核心是**语义相近的文本，向量距离也近**：

```text
"怎么请年假"  ≈  "年假申请流程"   （词不同，语义近）
"Python 爬虫"  ≉  "健身教程"      （词面近，语义远？实际视模型）
```

## 3. 为什么不能暴力全量比较

1000 万文档 × 1000 维向量，暴力算相似度太慢。
工业界用**近似最近邻（ANN）**，牺牲少量精度换速度：

| 算法 | 思路 | 特点 |
|------|------|------|
| HNSW | 多层跳表式图结构 | 召回率高、内存大，主流选择 |
| IVF | 聚类后只在附近桶里搜 | 省内存，召回略降 |
| PQ | 向量量化压缩 | 内存极小，精度损失 |
| ScaNN | 分桶 + 打分优化 | Google 出品 |

## 4. Embedding 的选择

搜索场景和 RAG 场景的 Embedding 要求类似：

- 中文场景优先选中文/双语模型（bge、m3e、qwen3-embedding）
- 向量维度：768~3072，越大越准也越贵
- **域适应**：通用模型在垂直领域（法律、医疗）效果可能差，需要微调

## 5. 向量检索的失效场景

1. **精确匹配失败**：搜"项目编号 ABC-001"，向量会把"ABC-001"和
   "ABC 公司 001 号文档"混为一谈
2. **稀有词/实体**：人名、型号、代码片段，语义向量学习不好
3. **冷启动**：新领域没有合适的 Embedding 模型
4. **可解释性差**：说不出"为什么相关"，排错困难

## 6. 混合检索（Hybrid Search）

当前生产标配：**BM25 召回 + 向量召回 + 融合**。

```
Query
 ├─ BM25 检索 → 结果A（字面匹配强）
 ├─ 向量检索 → 结果B（语义匹配强）
 └─ 融合（RRF / 加权） → 候选集 → （可选）精排 → Top-K
```

### 6.1 RRF：倒数排名融合

```text
score(d) = Σ  1 / (k + rank(d))
           r∈结果集
```

取 k=60：

```text
文档在 BM25 排第 1：1/(60+1) ≈ 0.0164
文档在向量排第 3：1/(60+3) ≈ 0.0159
总分 ≈ 0.0323
```

RRF 的优势：**不要求两种分数可比**（BM25 和余弦相似度单位完全不同），
只看排名。

### 6.2 加权融合

```text
score = α × norm(BM25) + β × cosine
```

需要把两种分数归一化到同一量纲，权重 α/β 用评估集调。

### 6.3 精排

融合后如果还要提升，用 Cross-Encoder 或 LTR 模型对 Top-50 精排。

## 7. 更进一步的检索技术

| 技术 | 做什么 | 适用 |
|------|--------|------|
| Query 改写 | LLM 把口语转成检索友好形式 | 搜索/Agent |
| Query 扩展 | 同义词、相关词补充 | 召回不足 |
| 学习型稀疏检索 | SPLADE 等，兼顾精确与语义 | 大厂方案 |
| 多路召回 | 图片/标签/向量/关键词并行 | 电商等复杂场景 |
| Rerank | 交叉编码器精排 | 精度敏感场景 |

## 8. 混合检索和 RAG 的关系

你在 RAG 里用的"混合检索"，底层就是这一课的技术：

```
Retriever（BM25 + 向量 + RRF）
  → Top-K 文档
  → 拼 Prompt
  → LLM 生成
```

搜索系统返回文档列表，RAG 返回生成答案；检索层完全一样。
