## 一、分层：UI / 逻辑 / 数据

借鉴你熟悉的 Web 分层（React 组件层 + Service + API），Flutter 项目按 feature 组织：

```text
lib/
├── main.dart
├── app/                      # App 级配置：主题、路由、ProviderScope
├── core/                     # 跨模块通用能力
│   ├── network/              # dio 封装、拦截器
│   ├── theme/                # 主题
│   ├── utils/                # 工具函数
│   └── widgets/              # 通用组件
└── features/                 # 按业务模块分
    ├── auth/
    │   ├── data/             # DTO、API 客户端
    │   ├── domain/           # 实体、Repository 接口
    │   └── presentation/     # 页面、Controller/Notifier、组件
    └── tasks/
        ├── data/             # TaskModel、TaskApi、本地数据库
        ├── domain/           # Task 实体、TaskRepository
        └── presentation/     # 列表页、详情页、TaskListNotifier
```

对应 Web 分层：

| Web | Flutter |
|-----|---------|
| React 页面 + Hooks | presentation（页面 + Notifier） |
| Service / 业务逻辑 | domain |
| Axios / API 层 | data |
| 依赖注入容器 | ProviderScope / Provider |

## 二、Repository 模式：隔离数据来源

```dart
// domain：定义接口（契约）
abstract class TaskRepository {
  Future<List<Task>> fetchTasks({String? projectId});
  Future<Task> createTask(Task task);
}

// data：网络实现
class TaskApiRepository implements TaskRepository {
  final Dio _dio;
  TaskApiRepository(this._dio);

  @override
  Future<List<Task>> fetchTasks({String? projectId}) async {
    final resp = await _dio.get('/api/tasks', queryParameters: {'project': projectId});
    return (resp.data['results'] as List)
        .map((e) => Task.fromJson(e))
        .toList();
  }
}

// data：Mock 实现（测试/开发用）
class TaskMockRepository implements TaskRepository {
  @override
  Future<List<Task>> fetchTasks({String? projectId}) async => mockTasks;
}

// Provider 统一提供，随时可替换实现
final taskRepositoryProvider = Provider<TaskRepository>((ref) {
  if (kDebugMode) return TaskMockRepository();
  return TaskApiRepository(ref.watch(dioProvider));
});
```

好处：

- UI 只依赖抽象，换数据源不影响页面
- 测试时注入 Mock
- 后续"网络 + 本地缓存"双实现时，页面零改动

## 三、选型对比：Riverpod vs Bloc vs GetX

| 维度 | Riverpod | Bloc | GetX |
|------|----------|------|------|
| 类型安全 | ✅ 强 | ✅ 强 | ⚠️ 弱（依赖字符串/全局） |
| 学习曲线 | 中 | 中高（Event/State 模式） | 低 |
| 可测试性 | ✅ Provider override | ✅ Bloc 纯逻辑 | 一般 |
| 生态现代度 | 高（官方推荐趋势） | 高（大厂项目多） | 争议多 |
| 代码量 | 少 | 多（样板代码） | 少 |

**选型结论（TaskFlow）**：

- 采用 **Riverpod**：类型安全、可测试、与 Future/Stream 天然契合
- 不用 Bloc：样板代码多，且我们已有 React 状态心智，Riverpod 更接近
- 不用 GetX：全局字符串依赖不利于长期维护，社区争议大

## 四、写一条 ADR（架构决策记录）

```markdown
# ADR-001：状态管理选型

## 状态
已接受（2026-08）

## 背景
TaskFlow 需要多页面共享登录态、任务列表、筛选条件；
需要支持异步加载与实时通知。

## 决策
使用 Riverpod（flutter_riverpod）作为状态管理方案。

## 备选
1. Provider：功能足够但粒度粗、依赖查找运行期报错
2. Bloc：类型安全但样板多，团队心智成本高
3. GetX：上手快但全局依赖难维护

## 后果
- 正向：类型安全、可测试、响应式依赖链
- 负向：需要学习 Riverpod 特有概念（Notifier/AsyncValue/autoDispose）
```

保存到 `learn-flutter/project/taskflow_app/docs/ADR-001-riverpod.md`。
