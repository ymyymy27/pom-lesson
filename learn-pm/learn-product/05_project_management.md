# 第5课：项目管理与敏捷开发

## 1. 产品经理与项目管理

### 为什么PM要懂项目管理？

```
产品经理 ≠ 项目经理，但需要具备项目管理能力

你设计了一个很好的功能，但：
  - 开发排不上期 → 需要优先级管理
  - 上线延期两周 → 需要进度管理
  - 上线后有bug  → 需要风险管理
  - 团队有分歧   → 需要沟通协调

产品经理是"产品的CEO"，对产品结果负责
  → 不仅要定义做什么，还要确保做出来
```

## 2. 敏捷开发（Scrum）

### 2.1 什么是敏捷？

```
瀑布模式（传统）：
  需求 → 设计 → 开发 → 测试 → 上线（几个月一个大版本）
  问题：周期长、变更难、风险高

敏捷模式（Scrum）：
  每 2 周一个迭代（Sprint），每次交付可用的功能
  快速验证 → 快速调整 → 持续改进

  Sprint 1: 核心功能    → 上线验证
  Sprint 2: 优化+新功能  → 上线验证
  Sprint 3: 继续迭代     → 上线验证
```

### 2.2 Scrum 核心概念

```
角色：
  Product Owner (PO)：  产品负责人（通常是PM），决定做什么
  Scrum Master (SM)：   流程教练，保障团队效率
  Development Team：    开发团队，决定怎么做

会议：
  Sprint Planning：     迭代计划会（确定本轮做什么）
  Daily Standup：       每日站会（15分钟，同步进度）
  Sprint Review：       迭代评审（展示成果给stakeholder）
  Sprint Retrospective：回顾会（总结改进点）

工具：
  Product Backlog：     产品需求池（所有待做的需求）
  Sprint Backlog：      本轮迭代的需求列表
  Burndown Chart：      燃尽图（剩余工作量趋势）
```

### 2.3 Sprint 流程

```
一个典型的 2 周 Sprint：

Day 1:  Sprint Planning（2-4小时）
        PO 讲解需求优先级
        团队评估工作量（故事点/人天）
        确定本轮 Sprint Backlog

Day 2-9: 开发 + 每日站会
        每天 15 分钟站会：
          昨天做了什么？
          今天计划做什么？
          有什么阻碍？

Day 10: Sprint Review（1-2小时）
        演示本轮成果
        收集反馈

Day 10: Sprint Retrospective（1小时）
        做得好的 → 继续保持
        做得不好的 → 改进措施
        下轮尝试什么新方法？
```

## 3. 需求管理

### 3.1 需求池管理

```
产品需求池（Product Backlog）：
  所有收集到的需求都放在这里
  PM 负责排优先级

需求状态流转：
  收集 → 评估 → 排期 → 开发中 → 测试中 → 已上线 → 已验证

管理工具：9--------------------------------------===
  飞书多维表格 / Jira / Linear / Notion
```

### 3.2 需求拆解

```
大需求（Epic）→ 故事（Story）→ 任务（Task）

示例：
  Epic: AI 聊天助手 v2.0
    ├── Story: 支持文件上传对话
    │     ├── Task: 前端上传组件开发
    │     ├── Task: 后端文件解析接口
    │     ├── Task: AI 模型接入文件内容
    │     └── Task: 测试用例编写
    ├── Story: 对话历史搜索
    │     ├── Task: 搜索 UI 设计
    │     ├── Task: 全文检索后端
    │     └── Task: 搜索结果高亮
    └── Story: 多模型切换
          ├── Task: 模型选择下拉框
          └── Task: 后端多模型路由
```

### 3.3 工作量评估

```
常用方法：故事点（Story Points）

斐波那契数列：1, 2, 3, 5, 8, 13, 21

  1点：几行代码就能搞定（1-2小时）
  2点：简单功能（半天）
  3点：中等功能（1天）
  5点：较复杂功能（2-3天）
  8点：复杂功能（一周）
  13点：很复杂，建议拆分
  21点：必须拆分

评估技巧：
  1. Planning Poker：团队成员各自出牌，差异大时讨论
  2. 相对估计：和已知任务比较（"这个比上次那个功能复杂吗？"）
  3. 不确定时估高：宁可提前完成，不要延期
```

## 4. 跨部门协作

### 4.1 PM 的协作对象

```
┌─────────────────────────────────────────────┐
│                产品经理                       │
├──────┬──────┬──────┬──────┬──────┬──────────┤
│ 设计 │ 前端 │ 后端 │ 测试 │ 运营 │ 老板/业务 │
│      │      │      │      │      │          │
│UI/UX │页面  │接口  │质量  │推广  │ 方向     │
│ 视觉 │ 交互 │ 数据 │ 验收 │ 增长 │ 资源     │
└──────┴──────┴──────┴──────┴──────┴──────────┘

和每个角色沟通的重点：
  设计师：产品目标 + 用户场景 + 参考竞品
  开发：  业务规则 + 异常流程 + 技术可行性
  测试：  验收标准 + 边界条件 + 优先级
  运营：  上线计划 + 数据目标 + 推广方案
  老板：  项目进展 + 数据结果 + 资源需求
```

### 4.2 沟通技巧

```
1. 金字塔原则（先说结论）
   ❌ "我们调研了用户，发现有些人觉得注册流程太长，
       然后我看了数据，注册转化率只有30%，所以..."
   ✅ "注册转化率只有30%，建议简化注册流程。
       根据调研，用户反馈注册步骤太多；
       数据显示，70%的用户在第3步流失。"

2. 需求沟通不要只说"做什么"
   ❌ "在这里加一个按钮"
   ✅ "用户反馈找不到XX功能入口（数据：XX%的用户...），
       建议在首页增加快捷入口，预期提升XX%的使用率"

3. 处理分歧
   - 回到用户和数据（"让数据说话"）
   - 如果无法判断，提议 A/B 测试
   - 尊重专业性（技术方案尊重开发，视觉尊重设计）
```

## 5. 产品上线

### 5.1 上线 Checklist

```
上线前：
  □ PRD 已更新到最新版
  □ 设计稿已确认
  □ 测试用例全部通过
  □ 性能测试通过（接口响应 < 200ms）
  □ 兼容性测试通过
  □ 数据埋点已部署并验证
  □ 灰度策略已确定
  □ 回滚方案已准备
  □ 相关方已通知（运营/客服/市场）
  □ 上线公告/更新日志已准备

上线中：
  □ 灰度放量（1% → 10% → 50% → 100%）
  □ 监控核心指标（错误率、响应时间）
  □ 关注用户反馈

上线后：
  □ 数据监控（至少观察 3 天）
  □ 用户反馈收集
  □ 上线复盘（数据是否达到预期？）
  □ 撰写数据报告
```

### 5.2 灰度发布策略

```
什么是灰度？
  不直接全量上线，先让一小部分用户使用新版本
  确认没问题后再逐步扩大范围

灰度策略：
  按百分比：1% → 5% → 20% → 50% → 100%
  按用户群：内部员工 → 种子用户 → 全量
  按地区：  先在一个城市上线 → 全国

灰度期间关注：
  1. 错误率是否上升
  2. 核心指标是否正常
  3. 用户是否有负面反馈
  4. 如有问题 → 立即回滚
```
