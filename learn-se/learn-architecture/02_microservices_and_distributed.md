## 1. SOA（面向服务架构）

### 1.1 原理

SOA 是微服务的 **前身**：把系统拆成 **粗粒度、可复用的服务**，通过 **企业服务总线（ESB）** 互联。

```
┌────────┐  ┌────────┐  ┌────────┐
│ 订单服务 │  │ 库存服务 │  │ 客户服务 │   ← 粗粒度、面向业务能力
└───┬────┘  └───┬────┘  └───┬────┘
    └──────┬────┴─────┬─────┘
       ┌───▼──────────▼───┐
       │   ESB 企业服务总线   │   ← 协议转换、路由、编排、监控
       └───┬──────────┬───┘
    ┌──────▼────┐ ┌───▼──────┐
    │ 遗留 ERP   │ │ 外部伙伴  │
    └───────────┘ └──────────┘
```

**拆的维度**：部署 + 通信——服务独立发布，但依赖中心总线做集成。

### 1.2 SOA vs 微服务

| 维度 | SOA | 微服务 |
|------|-----|--------|
| 服务粒度 | 粗（整段业务能力） | 细（单一限界上下文） |
| 集成方式 | 中心化 ESB | 去中心化（HTTP/gRPC/消息） |
| 数据 | 常共享数据库 | 每服务独立库 |
| 协议 | SOAP/WSDL 为主 | REST/gRPC/事件为主 |
| 团队模型 | 中央集成团队 | 全功能小队（Team Topologies） |
| 典型时代 | 2000s 企业 IT | 2010s 互联网/cloud-native |

### 1.3 何时用 / 何时别用

- **历史价值**：理解「为什么 ESB 被事件驱动取代」——总线易成单点瓶颈和「上帝组件」
- **今天仍可见**：大型传统企业遗留集成、银行/制造的多系统互联
- **别在新项目照搬 SOA**：现代替代是 **微服务 + 消息队列/事件总线（Kafka）**，集成去中心化

### 1.4 从 SOA 到微服务的演进

```
SOA：粗服务 + ESB 中心编排  →  瓶颈在总线、服务边界模糊
微服务：细服务 + 智能端点 dumb pipe  →  总线只做传输，业务逻辑在服务端
事件驱动：进一步解耦，订阅代替编排
```

## 2. 微服务架构

### 定义
将应用拆分为一组**小型、独立部署**的服务，每个服务围绕业务能力组织，通过轻量通信机制协作。

```
                    ┌─────────────┐
                    │ API Gateway │
                    └──────┬──────┘
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
    ┌────────────┐  ┌────────────┐  ┌────────────┐
    │ User Svc   │  │ Order Svc  │  │ Payment Svc│
    │  + DB      │  │  + DB      │  │  + DB      │
    └────────────┘  └────────────┘  └────────────┘
         独立部署、独立扩展、独立数据库
```

### vs 单体

| 维度 | 单体 | 微服务 |
|------|------|--------|
| 部署 | 整体 | 独立 |
| 扩展 | 整体 | 按服务 |
| 技术栈 | 统一 | 可异构 |
| 数据 | 共享 DB | 每服务独立 DB |
| 通信 | 函数调用 | 网络（HTTP/gRPC/消息） |
| 复杂度 | 低 | 高（网络、分布式事务） |
| 团队 | 小团队 | 多团队（Conway's Law） |

## 3. 服务拆分原则

### 2.1 按业务能力（DDD 限界上下文）

```
电商系统：
├── 用户服务（注册、登录、Profile）
├── 商品服务（Catalog、Inventory）
├── 订单服务（下单、状态）
├── 支付服务（支付、退款）
└── 通知服务（邮件、短信）
```

### 2.2 拆分信号

**适合拆分：**
- 模块有独立的扩展需求（搜索 QPS 远高于其他）
- 不同团队负责不同模块
- 模块技术栈需求不同（Python ML + Go 网关）

**不适合拆分：**
- 模块间频繁强一致事务
- 团队 < 8 人
- 业务边界尚不清晰

### 2.3 拆分反模式

| 反模式 | 问题 |
|--------|------|
| 按技术层拆分 | auth-service + db-service（不是业务能力） |
| 纳米服务 | 每个 CRUD 一个服务，运维爆炸 |
| 分布式单体 | 微服务架构但共享一个数据库 |

## 4. 服务间通信

### 3.1 同步通信

**REST API：**
```
GET /users/123
POST /orders {"user_id": 123, "items": [...]}
```

**gRPC（高性能内部通信）：**
```protobuf
service UserService {
  rpc GetUser (GetUserRequest) returns (User);
}
```

| | REST | gRPC |
|---|------|------|
| 格式 | JSON | Protobuf（二进制） |
| 性能 | 较低 | 高 |
| 浏览器 | 直接支持 | 需 grpc-web |
| 场景 | 外部 API | 服务间内部 |

### 3.2 异步通信

通过消息队列/事件总线解耦（详见第3课）。

### 3.3 通信选型

```
需要立即响应？ → 同步（REST/gRPC）
可以异步处理？ → 消息队列
广播通知？     → 发布/订阅
```

## 5. API 网关

### 作用
所有外部请求的**统一入口**。

```
Client → API Gateway → 内部服务
              │
              ├── 路由
              ├── 认证/鉴权
              ├── 限流
              ├── 日志
              └── 协议转换
```

**常见实现：** Kong, Nginx, AWS API Gateway, Traefik

### 网关 vs BFF

| | API Gateway | BFF (Backend for Frontend) |
|---|------------|---------------------------|
| 面向 | 通用 API | 特定客户端（Web/App） |
| 聚合 | 简单路由 | 为前端聚合多个服务数据 |
| 数量 | 通常 1 个 | 每种客户端 1 个 |

## 6. 服务发现与负载均衡

### 问题
微服务实例动态增减，如何知道该调用谁？

### 方案

**客户端发现：**
```
Service A → 查询 Registry → 获得 Service B 地址列表 → 负载均衡 → 调用
```

**服务端发现（更常见）：**
```
Service A → Load Balancer/K8s Service → 自动路由到 Service B 实例
```

**Kubernetes 中的实现：**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: user-service
spec:
  selector:
    app: user-service
  ports:
    - port: 80
      targetPort: 8080
```

## 7. 分布式系统的挑战

### 6.1 网络不可靠

- 超时、重试、熔断
- 幂等性设计（同一请求多次执行结果相同）

### 6.2 分布式事务

**问题：** 订单服务扣库存 + 支付服务扣款，如何保证原子性？

**方案：**

| 方案 | 说明 | 复杂度 |
|------|------|--------|
| 2PC（两阶段提交） | 协调者统一提交/回滚 | 高，性能差 |
| Saga | 每步本地事务 + 补偿 | 中 |
| 最终一致性 | 接受短暂不一致 | 低，需业务容忍 |

**Saga 示例：**
```
下单 Saga:
1. 创建订单（Order Svc）     → 成功
2. 扣库存（Inventory Svc）   → 成功
3. 扣款（Payment Svc）       → 失败
4. 补偿：恢复库存            → 回滚
5. 补偿：取消订单            → 回滚
```

### 6.3 熔断器（Circuit Breaker）

```
正常 → 失败次数超阈值 → 熔断（快速失败）→ 超时后半开 → 试探 → 恢复/继续熔断
```

**工具：** Hystrix, resilience4j, Polly

```python
# 伪代码
if circuit_breaker.is_open("payment-service"):
    return fallback_response()
try:
    result = payment_service.charge(amount)
    circuit_breaker.record_success("payment-service")
    return result
except TimeoutError:
    circuit_breaker.record_failure("payment-service")
    return fallback_response()
```

## 9. Conway's Law

> 设计系统的组织，其产生的设计等价于组织的沟通结构。

```
4 个团队 → 自然产生 4 个服务
2 个团队做 8 个服务 → 沟通成本爆炸
```

**启示：** 服务拆分应匹配团队结构（Team Topologies）。

# 深入篇：微服务与分布式的底层逻辑

## 1. 微服务的本质：把"部署边界"变成"团队边界"

微服务不是技术选择，是**组织选择**。Conway's Law 的实操版：

```
一个团队能独立交付 = 这个团队拥有完整的一条"竖切"（代码 + 数据 + 部署）
拆分的单位 = 团队能长期独立维护的最小业务域
```

所以拆服务前先问组织问题，再问技术问题：

1. 这个团队能独立负责"用户"从模型到 API 到数据库吗？
2. 这个业务域的变更频率、扩展需求和其他域真的不同吗？
3. 团队小于 8 人？→ 拆分大概率是灾难（运维成本摊到每个人头上）。

**微服务的真正收益不是"技术先进"，而是"组织解耦"**——
每个团队能独立发布、独立扩缩容、独立选型。

## 2. 拆分维度的深层：三个信号 vs 三个禁忌

**值得拆的三个信号：**

1. **扩展曲线不同**——搜索 QPS 是订单的 100 倍，混在一起 = 一起扩展浪费；
2. **故障边界不同**——直播模块崩了不该拖垮课程购买；
3. **合规/安全边界**——支付需要 PCI 隔离，不能和业务代码同库。

**拆不得的三个禁忌：**

1. **按技术层拆**（auth-service、db-service）——技术层没有业务边界，拆了全是分布式调用；
2. **纳米服务**（每个 CRUD 一个服务）——运维爆炸，收益为零；
3. **分布式单体**（微服务架构 + 共享数据库）——服务边界是假的，数据还耦合着，
   却付出了所有分布式代价——这是最贵的一种错误。

## 3. 通信选型的深层：同步 vs 异步的隐藏代价

```
同步（REST/gRPC）：
  好处：即时响应、直观、容易调试
  代价：调用链上的任何一个服务慢/挂，上游跟着慢/挂（级联失败）

异步（消息/事件）：
  好处：时间解耦、故障隔离、削峰
  代价：最终一致、重复消费、追踪困难（链路断在队列里）
```

**选型判断**：先问"调用方能接受延迟和失败吗？"

- 用户点按钮要即时结果 → 同步；
- "后续要做的事"（通知、统计、发邮件）→ 异步；
- 一个事件要喂多个下游 → 发布订阅（事件驱动）。

**混合是常态**：核心链路同步 + 旁路异步（核心下单同步，通知/分析异步）。

## 4. 分布式事务的深层：为什么 Saga 赢了 2PC

2PC 的问题不是"能不能做"，而是：

1. **锁持有时间长**——所有参与者锁着资源等协调者，性能差；
2. **协调者本身是单点**——它挂了，所有事务悬死；
3. **网络分区下无法保证**——协调者和参与者失联时，没人知道该提交还是回滚。

Saga 放弃"全局原子性"，接受"最终一致 + 补偿"：

```
每个步骤 = 本地事务 + 发布事件
失败时 = 反向执行补偿（取消订单、恢复库存、退款）
```

**编排 vs 编舞：**

| | 编排（Orchestration） | 编舞（Choreography） |
|---|---|---|
| 协调者 | 有（中央 Saga 协调器） | 无（每个服务听事件自行反应） |
| 可读性 | 流程集中、好懂 | 流程散落在各服务 |
| 耦合 | 服务不互知 | 服务靠事件契约耦合 |
| 适用 | 流程固定、需要强控 | 流程会演进、团队自治 |

**推荐**：流程复杂用编排（可读、可测），团队自治用编舞（去中心）。

## 5. 网关与服务发现的深层

**网关不是路由表，是"边界"**：

- 对外边界：认证、限流、协议转换、防攻击；
- 对内边界：隐藏服务拓扑（客户端不知道服务有 3 个实例）；
- 别忘了 BFF：客户端差异大时，网关做不了"为前端聚合数据"的活。

**服务发现两种模式**：

```
客户端发现：调用方自己查注册表 + 自己做负载均衡
  → 更少一跳，但每个语言都要实现客户端库
服务端发现（K8s Service）：负载均衡器帮你查
  → 简单，但多一跳，且 LB 要高可用
```

**现代默认**：K8s Service + Ingress——除非你需要极低延迟或自定义负载策略。

## 6. 微服务什么时候是"错误答案"

诚实清单（对照你自己的项目）：

- 团队 < 8 人 → 错；
- 业务边界不清 → 错；
- 模块间强事务频繁 → 错；
- 没有监控/可观测性基础 → 错（拆了等于盲飞）；
- 没有独立部署流水线 → 错（"微服务 + 一起发版"是最贵笑话）。

**正确路径永远是**：模块化单体 → 遇到真实痛点 → 绞杀者模式逐步拆（见第 4 课）。
