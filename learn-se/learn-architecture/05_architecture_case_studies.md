## 案例 1：初创 SaaS — 从 0 到 1

### 背景

```
产品：在线项目管理工具（类似 Notion + Jira 简化版）
团队：3 后端 + 2 前端 + 1 PM
用户：0 → 目标 6 个月内 1 万付费用户
预算：云服务 $500/月
```

### 推荐架构

```
Phase 1（0-3 月）：模块化单体

  ┌─────────────────────────────────┐
  │        Django/FastAPI Monolith   │
  │  ┌───────┐ ┌───────┐ ┌───────┐ │
  │  │ User  │ │Project│ │ Task  │ │
  │  │Module │ │Module │ │Module │ │
  │  └───────┘ └───────┘ └───────┘ │
  └──────────────┬──────────────────┘
                 ↓
         PostgreSQL + Redis

  理由：
  - 3 人团队，微服务运维成本太高
  - 模块间边界清晰，未来可拆
  - $500/月 足够（1 台 App + 1 台 DB）
```

### 关键 ADR

```markdown
# ADR-001: 选择模块化单体而非微服务

## 决策：模块化单体
## 理由：团队 3 人，6 个月内不需要独立扩展
##  revisit 触发条件：团队 > 8 人 OR 单模块 QPS > 1000
```

### 3 个月后的演进信号

```
如果出现以下情况，考虑拆分：
  □ 部署一次需要 30+ 分钟
  □ 某个模块的 bug 导致全站不可用
  □ 团队 2 人同时改同一模块冲突频繁
  □ 某个模块需要不同的扩展策略
```

## 案例 2：中型平台 — 服务化拆分

### 背景

```
产品：在线教育平台（课程 + 直播 + 作业 + 支付）
团队：20 后端 + 10 前端 + 5 QA
用户：100 万注册，5 万 DAU
痛点：部署慢、直播模块需要 GPU、支付合规隔离
```

### 推荐架构

```
                    ┌─────────────┐
                    │ API Gateway │
                    └──────┬──────┘
           ┌───────────────┼───────────────┐
           ↓               ↓               ↓
    ┌──────────┐   ┌──────────┐   ┌──────────┐
    │  Course  │   │  Live    │   │ Payment  │
    │  Service │   │  Service │   │ Service  │
    │ (Monolith│   │ (独立扩展 │   │ (合规隔离│
    │  剩余)   │   │  GPU)    │   │  PCI)    │
    └──────────┘   └──────────┘   └──────────┘
           │               │               │
           └───────────────┼───────────────┘
                    ┌──────┴──────┐
                    │    Kafka    │
                    └─────────────┘

拆分策略：绞杀者模式
  1. 先拆 Live（资源需求不同）
  2. 再拆 Payment（合规要求）
  3. 其余保持模块化单体
```

### DDD 上下文地图

```
┌─────────┐  ACL   ┌─────────┐
│ Course  │──────→│  Live   │
│(核心域)  │       │(核心域)  │
└────┬────┘       └────┬────┘
     │                 │
     │    ┌─────────┐  │
     └───→│ Payment │←─┘
          │(通用域)  │
          └─────────┘
```

### 关键权衡

| 决策 | 选择 | 理由 |
|------|------|------|
| 直播协议 | WebRTC + SFU | 低延迟，支持 500 人教室 |
| 消息队列 | Kafka | 课程进度事件、支付回调 |
| 剩余模块 | 保持单体 | 20 人中 12 人维护单体更高效 |
| 数据库 | 每服务独立 PG | Payment 合规隔离 |

## 案例 3：大型系统 — 高可用设计

### 背景

```
产品：金融支付平台
要求：99.99% 可用性（年停机 < 52 分钟）
      强一致（不能丢单、不能重复扣款）
      监管合规（审计日志、数据隔离）
团队：100+ 工程师，10 个 Squad
```

### 推荐架构

```
┌─────────────────────────────────────────────────────┐
│                   Multi-Region                       │
│  ┌──────────────┐         ┌──────────────┐          │
│  │  Region A    │         │  Region B    │          │
│  │  (Primary)   │ ←sync→  │  (Standby)   │          │
│  │              │         │              │          │
│  │ ┌──────────┐ │         │ ┌──────────┐ │          │
│  │ │ Payment  │ │         │ │ Payment  │ │          │
│  │ │ (Active) │ │         │ │(Standby) │ │          │
│  │ └──────────┘ │         │ └──────────┘ │          │
│  └──────────────┘         └──────────────┘          │
└─────────────────────────────────────────────────────┘

关键设计：
  1. 幂等性：每个支付请求带 idempotency_key
  2. 分布式事务：Saga + 补偿（不用 2PC）
  3. 审计：Event Sourcing，所有状态变更可追溯
  4. 多活：Region A 故障 → 30 秒内切到 Region B
  5. 限流：Token Bucket，防止雪崩
```

### 幂等性设计

```python
def process_payment(idempotency_key: str, amount: float, user_id: int):
    # 1. 查是否已处理
    existing = db.get_by_key(idempotency_key)
    if existing:
        return existing.result  # 直接返回之前的结果

    # 2. 加分布式锁
    with redis_lock(f"pay:{idempotency_key}", timeout=30):
        # 3. 再次检查（double-check）
        existing = db.get_by_key(idempotency_key)
        if existing:
            return existing.result

        # 4. 执行支付
        result = payment_gateway.charge(amount)

        # 5. 记录结果
        db.save(idempotency_key, result)
        return result
```

## 案例 4：AI 应用 — RAG 问答平台

### 背景

```
产品：企业知识库问答（RAG）
团队：5 后端 + 2 ML + 2 前端
用户：500 企业客户，每客户 100-10000 文档
要求：p95 首 token < 2s，答案可溯源，数据隔离
```

### 推荐架构

```
┌──────────┐     ┌─────────────┐     ┌──────────────┐
│  Client  │────▷│  API Gateway │────▷│  Chat Service│
└──────────┘     └─────────────┘     └──────┬───────┘
                                            │
                    ┌───────────────────────┼───────────────────┐
                    ▼                       ▼                   ▼
             ┌──────────┐           ┌──────────┐         ┌──────────┐
             │ Ingestion│           │ Retrieval│         │ LLM Proxy│
             │ Pipeline │           │ Service  │         │ Service  │
             └────┬─────┘           └────┬─────┘         └────┬─────┘
                  │                      │                    │
                  ▼                      ▼                    ▼
             ┌──────────┐           ┌──────────┐         ┌──────────┐
             │ Object   │           │ Vector DB│         │ LLM API  │
             │ Storage  │           │(Pinecone)│         │(OpenAI)  │
             └──────────┘           └──────────┘         └──────────┘

关键设计：
  1. Ingestion 异步：上传 → 解析 → 分块 → Embedding → 索引
  2. Retrieval 与 Generation 分离（可独立扩展/替换模型）
  3. 多租户：tenant_id 贯穿索引和查询
  4. LLM Proxy：统一限流、缓存、Fallback 模型
  5. 溯源：返回答案 + 引用 chunk 来源
```

### 关键 ADR

```markdown
# ADR-003: 采用异步 Ingestion Pipeline

## 决策
文档上传后异步处理，不阻塞 API

## 理由
- 大 PDF 解析可能 30s+
- 用户期望：上传后立即返回 job_id，处理完通知
- 可独立扩展 Worker 数量

## 触发条件
单文档 > 10MB 或 批量导入 > 100 文件
```

```
业务匹配：
  □ 架构支持当前业务规模？
  □ 6 个月后的增长能应对吗？

  □ 可用性目标多少？有单点故障吗？
```

# 深入篇：案例背后的决策方法论

## 1. 四个案例的共同决策框架

四个案例表面是四个系统，实际是同一套决策框架的四次应用：

```
1. 摸清约束：团队规模？资金？合规？用户量？
2. 找当前最大约束：什么在拖慢你？（不是"什么技术最酷"）
3. 选最小解：只解决当前约束，留好下一步的退路
4. 写 ADR：把"为什么"钉在纸上，设 revisit 触发条件
```

| 案例 | 当前最大约束 | 最小解 | 下一步触发 |
|---|---|---|---|
| 初创 SaaS | 团队 3 人、验证产品 | 模块化单体 | 团队>8 或单模块 QPS>1000 |
| 中型平台 | 直播扩展失衡 + 支付合规 | 只拆 Live 和 Payment | 其余模块冲突加剧 |
| 金融平台 | 99.99% 可用 + 强一致 | 幂等 + Saga + 多活 | 审计需求升级 |
| RAG 平台 | 大文档解析阻塞 + 检索质量 | 异步摄取 + 检索/生成分离 | 单文档>10MB |

## 2. 反事实分析：每个案例"选错了会怎样"

这是案例课最有价值的一层——**理解反面**：

**初创 SaaS 选微服务** → 3 人团队运维 8 个服务 + 3 个数据库 + 服务网格，
交付速度降到原来的 1/3，产品可能死在验证期。

**中型平台不拆直播** → 直播的 GPU 需求逼着整个单体上 GPU 实例，
成本 ×5；直播故障拖垮课程购买（故障边界没隔离）。

**金融平台用 2PC** → 高峰时锁等待把支付打挂，协调者单点故障 = 全局不可用。

**RAG 平台同步摄取** → 用户上传 30MB PDF 被阻塞 30 秒，首请求超时，
产品口碑死于体验。

**反事实训练法**：每看到一个推荐架构，都问"如果选另一个，系统在哪一步先死？"
——这比记住"该选什么"有用得多。

## 3. 从案例到方法论：三个可复用的工具

### 3.1 演进信号清单（抄到你的项目里）

```
□ 部署一次要 30+ 分钟
□ 一个模块的 bug 导致全站不可用
□ 两个人改同一个模块频繁冲突
□ 某个模块的扩展需求和其他模块差异巨大
□ 某个模块需要不同的合规/安全级别
□ 某个模块需要不同的技术栈
出现任意 2 条 → 该考虑拆分了
```

### 3.2 幂等性模板（分布式写入必备）

```python
def process_with_idempotency(key, fn):
    if existing := db.get_by_key(key):
        return existing.result              # 已处理：直接返回
    with redis_lock(f"idem:{key}"):         # 防并发双写
        if existing := db.get_by_key(key):  # double-check
            return existing.result
        result = fn()
        db.save(key, result)
        return result
```

### 3.3 架构评审四问（任何设计交付前）

```
1. 当前最大约束是什么？这个设计解的是它吗？
2. 最坏情况（流量×10 / 服务挂 1 个）会发生什么？
3. 我的"下一步退路"是什么？演进路径清晰吗？
4. 3 个月后，我能向新人解释为什么这么设计吗？（ADR）
```

## 4. 案例课的最终心法

> **架构不是选"最好的方案"，是选"当前约束下代价最小的方案"。**
> 每个案例的正确答案，换一批约束就会变成错误答案。
> 所以学案例，学的是"读约束"和"算代价"，不是背架构图。
