# 设计模式全景图

## 1. 设计模式是什么？

### 一句话解释
**设计模式是前人总结的「反复出现的优秀设计方案」** —— 不是发明新东西，而是给常见问题起名字、给解法写配方。

### 类比

| 领域 | 模式 |
|------|------|
| 建筑 | 拱门、柱廊、中庭 |
| 烹饪 | 炒、蒸、炖（固定流程，换食材） |
| 编程 | 单例、工厂、观察者（固定结构，换业务） |

### 模式的组成

每个模式通常包含四要素：

1. **名称** — 便于沟通（「这里用观察者」）
2. **问题** — 什么场景下出现
3. **解决方案** — 类/对象的组织方式
4. **效果** — 优点与代价

## 3. 快速对照表

| 模式 | 一句话 | 典型场景 |
|------|--------|---------|
| 单例 | 全局唯一实例 | 配置、连接池、日志 |
| 工厂方法 | 子类决定创建哪种对象 | 文档导出（PDF/Word） |
| 抽象工厂 | 创建一系列相关产品 | UI 主题（Dark/Light 组件族） |
| 建造者 | 分步构建复杂对象 | SQL 构建器、HTTP 请求 |
| 原型 | 克隆已有对象 | 深拷贝、游戏对象复制 |
| 适配器 | 旧接口适配新接口 | 第三方 SDK 封装 |
| 桥接 | 抽象与实现分离 | 跨平台渲染 |
| 组合 | 树形结构统一对待 | 文件系统、菜单 |
| 装饰器 | 动态添加职责 | 中间件、流包装 |
| 外观 | 简化复杂子系统 | API Gateway |
| 享元 | 共享细粒度对象 | 文本编辑器字符对象 |
| 代理 | 控制对象访问 | 懒加载、权限、缓存 |
| 责任链 | 请求沿链传递 | 中间件、审批流 |
| 命令 | 请求封装为对象 | 撤销/重做、任务队列 |
| 观察者 | 一对多通知 | 事件系统、MVC |
| 状态 | 行为随状态变化 | 订单状态机、TCP 连接 |
| 策略 | 算法可互换 | 排序、支付方式、折扣 |
| 模板方法 | 骨架固定，步骤可变 | 框架钩子、数据处理流程 |
| 迭代器 | 统一遍历方式 | for-each 抽象 |
| 中介者 | 对象间通过中介通信 | 聊天室、对话框组件 |
| 备忘录 | 保存/恢复状态 | 编辑器撤销 |
| 访问者 | 操作与结构分离 | AST 遍历、编译器 |
| 解释器 | 语法规则解释执行 | 表达式引擎、正则 |

## 4. 选型决策树

```
问题是什么？
│
├─ 创建对象太复杂/需要灵活？
│   ├─ 只需一个实例 → 单例
│   ├─ 创建逻辑要子类决定 → 工厂方法
│   ├─ 创建一族相关产品 → 抽象工厂
│   ├─ 构建步骤多且可选 → 建造者
│   └─ 复制已有对象 → 原型
│
├─ 接口/结构不匹配？
│   ├─ 旧接口换新接口 → 适配器
│   ├─ 抽象与实现独立变化 → 桥接
│   └─ 树形结构统一处理 → 组合
│
├─ 需要扩展功能？
│   ├─ 动态叠加能力 → 装饰器
│   ├─ 简化复杂调用 → 外观
│   └─ 控制访问/延迟加载 → 代理
│
└─ 对象如何协作？
    ├─ 算法要可切换 → 策略
    ├─ 行为随状态变 → 状态
    ├─ 一对多通知 → 观察者
    ├─ 操作要可撤销 → 命令
    ├─ 流程固定步骤可变 → 模板方法
    └─ 请求沿链处理 → 责任链
```

## 5. UML 类图速查

### 5.1 关系符号

```
───▷  继承（泛化）      Animal ◁── Dog
───◇  实现（接口）      Flyable ◇── Bird
────▷  关联             User ──▷ Order
────▷  依赖（使用）      Service ··▷ Repository
───◇  聚合（弱拥有）     Team ◇── Player
───◆  组合（强拥有）     House ◆── Room
```

### 5.2 常见模式 UML 骨架

**策略模式：**
```
        ┌─────────────┐
        │  Context    │
        │─────────────│
        │ - strategy  │──────▷ Strategy (interface)
        │ + execute() │              △
        └─────────────┘         ┌────┴────┐
                           ConcreteA  ConcreteB
```

**观察者模式：**
```
Subject ──▷ Observer (interface)
  │              △
  │ notify    ConcreteObserver
  ▼
observers: List[Observer]
```

**工厂方法：**
```
Creator (abstract)          Product (interface)
  + factory_method() ──▷         △
  + operation()            ConcreteProduct
        △
  ConcreteCreator
```

## 6. 何时用 / 何时不用

### 使用模式的前提

1. **问题真实存在** — 不是「可能将来需要」
2. **简单方案不够** — if/else 或函数参数能解决就不要上模式
3. **团队理解成本可接受** — 模式是沟通语言，不是炫技

### 常见误用

| 误用 | 正确做法 |
|------|---------|
| 到处单例 | 依赖注入 + 作用域管理 |
| 简单对象用建造者 | 直接构造函数 |
| 两个类用抽象工厂 | 简单工厂或字典映射 |
| 每个 if 变策略 | 3 个以上分支且频繁扩展时才考虑 |

### 规则 thumb

> **Rule of Three：** 第三次遇到相同结构时再抽象成模式。

# 深入篇：设计模式的底层逻辑

> 前面的内容回答了"模式是什么、有哪些"；这一篇回答"为什么它们长这样"。
> 建议至少学完 01~03 再回来看，会有第二次顿悟。

## 1. 三层理解框架：形状 → 意图 → 变化点

同一个"接口 + 实现 + 持有者"的形状，可以是工厂、策略、装饰器、代理、桥接……
只记形状必然混乱。理解任何模式都按三层走：

```
第一层 形状：类/接口怎么组织（静态结构）
第二层 意图：它想解决什么问题（这是 GoF 分类的依据）
第三层 变化点：它隔离了什么变化（这是"为什么值得存在"）
```

例：装饰器和代理形状几乎一样（都实现接口、都持有引用）。
- 装饰器意图：增强功能 → 变化点是"功能叠加方式"；
- 代理意图：控制访问 → 变化点是"访问策略"。

**判断模式时问"意图"，永远不要问"长得像谁"。**

## 2. 封装变化：所有模式的唯一共同命题

软件唯一不变的是"它会变"。设计模式的本质是回答一个问题：

> **当系统某部分要变化时，怎么让其余部分几乎不用动？**

每个模式 = 在一个变化点上开口子：

| 模式 | 开在哪个变化点 |
|---|---|
| 工厂 | 创建哪个对象 |
| 策略 | 用哪个算法 |
| 装饰器 | 叠加哪些功能 |
| 观察者 | 谁关心事件 |
| 状态 | 行为随状态怎么流转 |
| 访问者 | 给稳定结构加什么操作 |

**思考工具**：遇到设计难题，先说出"什么在变、什么不变"。
说不出来，就不该用模式。

## 3. 复杂度住哪边：模式的"投票"逻辑

每个模式都是一次"复杂度该住哪边"的投票——让频繁变化的那一边变便宜：

| 模式 | 复杂度住哪边 | 换来什么便宜 |
|---|---|---|
| 工厂 | 工厂侧 | 加产品类型便宜 |
| 装饰器 | 装饰器侧 | 加功能便宜 |
| 状态 | 状态类侧 | 加状态便宜 |
| 访问者 | Visitor 侧 | 加操作便宜 |
| 组合 | 节点侧 | 加节点便宜 |

代价永远在反面：访问者让"加操作"便宜，就必然让"加节点"变贵。
**没有免费的模式，只有划算的权衡。**

## 4. SOLID 与模式的真实关系

不是"模式实现了 SOLID"，而是"模式是 SOLID 的具体应用"：

| 原则 | 一句话 | 模式例子 |
|---|---|---|
| SRP 单一职责 | 一个类只做一件事 | 策略（算法独立）、外观（编排独立） |
| OCP 开闭原则 | 对扩展开放、对修改关闭 | 工厂、装饰器、策略、状态、访问者 |
| LSP 里氏替换 | 子类必须能替换父类 | 所有"面向接口"的模式的前提 |
| ISP 接口隔离 | 客户端不该依赖不需要的接口 | 适配器、桥接 |
| DIP 依赖倒置 | 高层不依赖低层，都依赖抽象 | 六边形架构、工厂、策略 |

**最值钱的一条是 OCP**：23 个模式里一大半，本质都是"把'加新东西'从'改旧代码'变成'加新代码'"。

## 5. 分类的深层逻辑：出生、组合、协作

三大类的划分不是任意的，它们是对象的三个生命周期阶段：

```
创建型：对象出生之前 —— 怎么把它造出来
结构型：对象出生之后 —— 它们以什么形状待在一起
行为型：它们活着的时候 —— 怎么通信、分工、配合
```

所以看到"两个类接口对不上"，先问：这是出生问题（创建型）、
组合问题（结构型）还是协作问题（行为型）？**这一分钟归类，能少走一半弯路。**

## 6. 不看名字识别模式的方法

在别人的代码/框架里认出模式，用四个问题：

1. **这个抽象隔离了什么变化？**（答不出 = 可能只是过度设计）
2. **谁是持有者，谁是被持有者？**（Context / Creator / Subject / 装饰器……）
3. **调用是单向、双向、还是递归？**（单向 → 外观/适配器；双向 → 中介者；递归 → 组合/解释器）
4. **如果去掉这层抽象，哪里会痛？**（加新类型要改哪里）

## 7. AI 时代怎么看设计模式

AI 开发里模式不但没过时，反而更密集：

- 各家模型 API → **适配器**；按配置选供应商 → **工厂**；
- 流式输出回调 → **观察者**；工具调用记录 → **命令**；
- Agent 生命周期 → **状态**；Agent 主循环 → **模板方法**；
- Guardrails 链 → **责任链**；`agent.run()` → **外观**；
- 对话检查点 → **备忘录**；多 Agent 调度 → **中介者**。

AI 时代真正变的是：**很多模式被框架内置了**（LangChain 的 callback、model wrapper），
你要做的不是手写，而是**认出它们、理解取舍、在需要时组合**。

## 8. 一句话总纲

> 设计模式 = 给变化留位置；面向抽象是手段，封装变化是目的；
> 复杂度住哪边是决策；意图大于结构；模式是手段，不是目标。
