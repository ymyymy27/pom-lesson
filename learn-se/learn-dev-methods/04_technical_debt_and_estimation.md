# 第4课：技术债、估时与风险管理

## 1. 技术债

### 定义

Ward Cunningham 的比喻：

> 走捷径就像借了一笔债。你获得了短期速度，但未来每次改动都要「还利息」—— 因为代码结构不佳，修改成本更高。

### 技术债象限

```
                    故意                无意
              ┌──────────────┬──────────────┐
    审慎      │  已知妥协     │  技术落后     │
              │  (MVP 先上线) │  (不知更好方案)│
              ├──────────────┼──────────────┤
    鲁莽      │  走捷径       │  混乱代码     │
              │  (Deadline)  │  (无规范)     │
              └──────────────┴──────────────┘
```

**可接受：** 审慎+故意（有记录的妥协，计划偿还）  
**不可接受：** 鲁莽+无意（既无计划也无意识）

### 技术债的表现

| 表现 | 影响 |
|------|------|
| 改一处动十处 | 开发速度下降 |
| 无人敢碰的模块 | 知识孤岛 |
| 无测试的代码 | Bug 频发 |
| 过时依赖 | 安全漏洞 |
| 复制粘贴重复 | 改一处漏多处 |
| 「临时方案」用了 3 年 | 利息累积 |

## 2. 技术债管理

### 2.1 识别

- **静态分析：** SonarQube, CodeClimate
- **团队反馈：** 「这个模块太难改了」
- **指标：** Bug 密度、变更失败率、部署频率下降

### 2.2 记录

```markdown
## Tech Debt Item #TD-042
**描述：** UserService 直接操作 SQL，无 Repository 层
**影响：** 换数据库需改 15 个文件
**产生原因：** MVP 赶工（ADR-003 已知妥协）
**建议方案：** 引入 Repository 模式
**估算：** 3 Story Points
**优先级：** 中（下次动 User 模块时一并做）
```

### 2.3 偿还策略

| 策略 | 说明 |
|------|------|
| 童子军规则 | 每次改动顺手改善 |
| 20% 规则 | 每个 Sprint 留 20% 容量还技术债 |
| 重构 Sprint | 专门一个 Sprint 做重构（谨慎使用） |
| 绞杀者 | 新功能用新架构，旧代码逐步替换 |

### 2.4 与 PO 沟通

```
❌ 「我们需要重构，别管功能了」
✅ 「UserService 重构需要 3 points，完成后新功能开发速度预计提升 40%，
    建议在 Sprint 12 安排，不影响本 Sprint 的支付功能交付」
```

**关键：** 用业务语言解释技术债的影响（速度、Bug、风险）。

## 3. 估时方法

### 3.1 为什么估时不准？

| 原因 | 说明 |
|------|------|
| 规划谬误 | 低估复杂度是人性 |
| 未知未知 | 没遇到过的技术问题 |
| 范围蔓延 | 需求不断加 |
| 中断 | 会议、Bug、支持 |
| 乐观偏差 | 「这次应该很快」 |

### 3.2 估时方法对比

| 方法 | 说明 | 适合 |
|------|------|------|
| Story Point | 相对大小 | Scrum 团队 |
| T-Shirt Size | S/M/L/XL | 早期粗略估算 |
| 三点估算 | 乐观/最可能/悲观 | 有历史数据 |
| 工时估算 | 绝对小时/天 | 固定范围项目 |
| #NoEstimates | 不估时，拆小 Story | 成熟敏捷团队 |

### 3.3 三点估算（PERT）

```
期望 = (乐观 + 4×最可能 + 悲观) / 6

例：登录功能
  乐观：2 天
  最可能：4 天
  悲观：8 天
  期望 = (2 + 4×4 + 8) / 6 = 4.3 天
```

### 3.4 拆小降低风险

```
❌ 「用户管理系统」→ 估 40 points（巨大不确定性）
✅ 拆为：
   - 用户注册：5 points
   - 用户登录：3 points
   - Profile 页：3 points
   - 密码重置：5 points
   → 每个估得准，总和才可信
```

### 3.5 估时最佳实践

1. **团队一起估** — Planning Poker，避免个人偏差
2. **参考历史** — Velocity 是最可靠的校准
3. **包含非编码时间** — Review、测试、部署、沟通
4. **定期校准** — 实际 vs 估算，调整基准
5. **范围明确** — DoD 清晰，减少「差不多」

## 4. 风险管理

### 4.1 风险矩阵

```
影响
 高 │  监控    │  优先处理  │
    │  (中风险) │  (高风险)  │
 低 │  忽略    │  简单应对  │
    └──────────┴──────────┘
      低          高
              概率
```

### 4.2 常见项目风险

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 关键人员离职 | 中 | 高 | 知识文档化、结对 |
| 第三方 API 变更 | 中 | 中 | 适配器模式、Mock |
| 需求大幅变更 | 高 | 中 | 敏捷迭代、Backlog |
| 性能不达标 | 中 | 高 | 早期性能测试 |
| 安全漏洞 | 低 | 高 | 安全扫描、Code Review |

### 4.3 风险应对策略

| 策略 | 说明 | 示例 |
|------|------|------|
| 规避 | 改变计划消除风险 | 不用不成熟的技术 |
| 转移 | 转给第三方 | 买 SaaS 而非自建 |
| 缓解 | 降低概率或影响 | 加测试、做 Spike |
| 接受 | 已知风险，准备预案 | 低影响 Bug 不阻塞发布 |

### 4.4 Spike（探针）

```
不确定的技术方案 → 限时 Spike（1-2 天）
  → 产出：可行性结论 + 原型代码（非生产代码）
  → 然后才正式估时和开发
```

## 5. 持续改进

### 5.1 Sprint Retrospective 框架

**Start-Stop-Continue：**
```
Start:  开始做什么？（如：PR 加测试截图）
Stop:   停止做什么？（如：Standup 超过 15 分钟）
Continue: 继续做什么？（如：结对 Review 复杂 PR）
```

**4Ls：**
```
Liked    — 喜欢的
Learned  — 学到的
Lacked   — 缺少的
Longed for — 希望的
```

### 5.2 度量驱动改进

| 指标 | 说明 | 目标方向 |
|------|------|---------|
| Deployment Frequency | 部署频率 | ↑ |
| Lead Time | 从 commit 到生产 | ↓ |
| Change Failure Rate | 变更失败率 | ↓ |
| MTTR | 平均恢复时间 | ↓ |
| Velocity | Sprint 完成点数 | 稳定 |
| Bug Escape Rate | 生产 Bug / 总 Bug | ↓ |

**DORA 四个关键指标**（DevOps Research and Assessment）就是前四项。

### 5.3 Blameless Postmortem

```
生产事故后：

❌ 「谁把生产搞崩的？」
✅ 「系统允许了什么导致这次事故？如何防止再次发生？」

模板：
1. 时间线（发生了什么）
2. 根因（5 Whys）
3. 影响（用户/业务）
4. 行动项（具体改进，有负责人和 deadline）
5. 经验教训
```

## 6. 工程效能

### 开发者体验（DX）清单

- [ ] 本地环境 30 分钟内可运行
- [ ] CI 反馈 < 10 分钟
- [ ] 有清晰的 README 和 CONTRIBUTING 指南
- [ ] 测试可靠且快速
- [ ] 部署一键完成
- [ ] 文档与代码同步

### 减少浪费（Lean）

| 浪费 | 表现 | 改进 |
|------|------|------|
| 等待 | PR 3 天没人 Review | Review SLA |
| 过度工程 | 简单功能过度设计 | YAGNI |
| 任务切换 | 同时开 5 个分支 | 限制 WIP |
| 重复工作 | 手动部署 | 自动化 |
| 缺陷 | 生产 Bug | 测试 + Review |

## 7. 动手练习

### 练习 1：技术债评估

以下哪些是「可接受的技术债」？哪些需要立即处理？

1. MVP 阶段用 SQLite 代替 PostgreSQL（计划 3 个月后迁移）
2. 复制粘贴的表单验证逻辑出现在 8 个页面
3. 生产环境有一个 `TODO: fix this hack` 存在了 2 年
4. 为赶 deadline 跳过了支付模块的测试

<details>
<summary>参考答案</summary>

1. **可接受** — 审慎+故意，有迁移计划
2. **需计划偿还** — 无意重复，下次改动时提取
3. **需立即处理** — 鲁莽+无意，生产 hack 风险高
4. **不可接受** — 支付是关键路径，无测试风险极高

</details>
