# 第5课：多租户隔离模型：三种方案怎么选

## 1. 一句话解释

多租户的核心是"共享多少、隔离多少"。三种主流方案——独立数据库、共享库独立 Schema、共享表加租户字段——本质是成本、运维复杂度与隔离强度之间的权衡。

## 2. 类比

```
独立数据库   = 每人一栋别墅（隔离最强，成本最高）
独立 Schema  = 每户独立套房（共用大楼水电，互不干扰）
共享表       = 合租单间（便宜，但必须守规矩）
```

## 3. 三种模型

### 3.1 独立数据库

每个租户一个数据库。

优点：

- 隔离最强，故障域独立
- 可独立备份、迁移、恢复
- 大租户可单独调优（索引、资源）

缺点：

- 成本高、运维复杂（数百上千租户时必须自动化建库/迁移）
- 跨租户统计困难
- DDL 变更要批量执行，版本管理复杂

### 3.2 共享库 + 独立 Schema

同一个数据库实例，每个租户一个 Schema，表结构相同。

优点：

- 物理上区分，隔离中等偏强
- 比独立库好运维，可整体备份
- 支持不同租户的数据按 Schema 清理

缺点：

- 共享实例，故障域未完全隔离
- 连接管理复杂，连接数会被租户数放大
- 某些托管数据库的 Schema 级迁移成本高

### 3.3 共享表 + tenant_id

所有租户同表，加 `tenant_id` 列。

优点：

- 成本最低、扩容租户最快
- 开发最简单，索引和查询统一

缺点：

- 最容易越权，漏一个过滤就串租户
- 备份/恢复只能全量
- 一个租户的大查询可能影响所有人

## 4. 选型矩阵

| 因素 | 独立库 | 独立 Schema | 共享表 |
|------|--------|-------------|--------|
| 客户少且大（企业级） | ✅ 推荐 | 可选 | 一般 |
| 客户多且小（SaaS 长尾） | 不推荐 | 可选 | ✅ 推荐 |
| 强合规/数据主权要求 | ✅ 推荐 | ✅ 推荐 | 不推荐 |
| 成本敏感 | 不推荐 | 可选 | ✅ 推荐 |
| 快速上线 MVP | 不推荐 | 可选 | ✅ 推荐 |

## 5. 混合与演进路径

常见路径：

```
MVP：共享表 + tenant_id（先跑通业务）
→ 大客户：迁移到独立 Schema / 独立数据库
→ 超大规模：租户路由表 + 分片
```

租户路由表：

```sql
CREATE TABLE tenant_routes (
  tenant_id BIGINT PRIMARY KEY,
  target TEXT NOT NULL  -- 'db:acme' / 'schema:acme' / 'shared'
);
```

迁移要点：双写、数据校验、切换窗口、回滚预案。独立库/独立 Schema 不是"一步到位"，而是给大客户准备的升级路径。
