# 第2课：故障响应与 Postmortem

## 1. 故障响应流程

```
告警触发
    ↓
On-call 工程师 Acknowledge（5 min 内）
    ↓
评估严重级别（P0-P3）
    ↓
┌─ P0/P1 ──→ 立即响应 → 组建 War Room → 修复 → 验证
└─ P2/P3 ──→ 工作时间处理
    ↓
恢复服务
    ↓
Postmortem（无责复盘，48h 内）
    ↓
改进行动项 → 跟踪落地
```

### 严重级别

| 级别 | 定义 | 响应时间 | 示例 |
|------|------|---------|------|
| P0 | 全站不可用 | 5 min | 数据库宕机、支付失败 |
| P1 | 核心功能不可用 | 15 min | 登录失败、下单失败 |
| P2 | 部分功能降级 | 1 hour | 搜索慢、通知延迟 |
| P3 | 轻微问题 | 下个工作日 | UI 错位、日志异常 |

## 2. On-call 最佳实践

```
轮值制度：
  - 1 主 + 1 备，每周轮换
  - 工作时间 Dev 负责，非工作时间 On-call 负责
  - 补偿：On-call 津贴 + 故障处理后调休

Runbook（运维手册）：
  每个告警都应有 Runbook：
  1. 告警含义
  2. 可能原因（Top 3）
  3. 排查步骤
  4. 临时缓解方案
  5. 升级路径

工具：
  PagerDuty / Opsgenie — 告警路由
  Statuspage — 对外状态页
  Slack/飞书 — War Room 频道
```

## 3. Postmortem（无责复盘）

### 模板

```markdown
# Postmortem: [故障标题]

## 概要
- 日期：2026-07-15
- 持续时间：14:30 - 15:45（75 分钟）
- 严重级别：P1
- 影响：30% 用户无法登录

## 时间线
| 时间 | 事件 |
|------|------|
| 14:30 | 监控告警：登录 API 5xx 率 > 10% |
| 14:35 | On-call Ack，开始排查 |
| 14:50 | 定位：Redis 连接池耗尽 |
| 15:10 | 缓解：重启 Redis + 扩大连接池 |
| 15:45 | 确认恢复，5xx 率 < 0.1% |

## 根因
Redis max_connections 默认 10000，连接泄漏导致池耗尽。
根因是 v2.3 引入的连接未正确 close（代码 bug）。

## 影响
- 约 15 万用户受影响
- 错误预算消耗 40%

## 改进行动
| 行动 | 负责人 | 截止日期 |
|------|--------|---------|
| 修复连接泄漏 bug | Alice | 7/17 |
| 添加 Redis 连接数监控 | Bob | 7/20 |
| 所有外部连接添加 context manager | Team | 7/31 |
| 添加连接泄漏集成测试 | Alice | 7/24 |

## 做得好的
- 15 分钟内定位根因
- Runbook 帮助快速排查

## 经验教训
- 连接池配置变更需要 load test 验证
- 缺少 Redis 连接数的提前告警
```

### 无责文化

```
✅ 「系统失败了」而非「某人犯错了」
✅ 关注流程和系统的改进
✅ 鼓励透明分享
❌ 追责、批评个人
❌ 隐藏或淡化故障
❌ Postmortem 后不跟踪行动项
```

## 4. 故障模式库

常见故障模式及预防：

| 故障模式 | 预防 |
|---------|------|
| 级联故障 | 熔断、超时、舱壁隔离 |
| 热点 | 分片、缓存、限流 |
| 数据不一致 | Saga、幂等、对账 |
| 配置错误 | 配置审查、渐进发布 |
| 依赖故障 | 降级、Fallback、Mock |
| 资源耗尽 | 限流、自动扩缩、监控 |
| 部署故障 | Canary、Feature Flag、快速回滚 |
