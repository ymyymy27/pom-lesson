# 第5课：NAT 穿透原理 —— 打洞、STUN、TURN 中继

## 1. 为什么"两台内网设备"不能直接连

回顾第 2 课：家用路由器只记录"由内向外"的连接映射。

```text
设备 A (192.168.1.10)         设备 B (192.168.2.10)
    │  NAT 路由器 A                NAT 路由器 B
    │  公网出口: 100.64.0.2       公网出口: 100.64.0.3
    └────────────── 互联网 ──────────────┘
```

A 向 B 发包时，只知道 B 的**私网地址** `192.168.2.10`——
互联网上根本没有这个地址；即使知道 B 路由器的公网出口 IP，
路由器 B 也没有为"入站新连接"建立映射，会直接丢弃。

所以"双方都没有公网 IP"时，**必须借助第三方**：要么打洞，要么中继。

---

## 2. 关键概念：NAT 映射

当 A 主动向外发起连接时，路由器 A 会记录一条映射：

```text
内部: 192.168.1.10:54321  →  外部: 100.64.0.2:54321
```

外部设备只要向 `100.64.0.2:54321` 发包，路由器就会转给 A 的
`192.168.1.10:54321`。

**NAT 穿透的核心思路就是：想办法让双方都往对方的"外部映射地址"发包。**

---

## 3. STUN：查自己的"外部地址"

### 3.1 STUN 是什么

**STUN（Session Traversal Utilities for NAT）** 是一个服务器，
回答一个问题：**"从外面看，我的公网 IP 和端口是什么？"**

```text
设备 A ──> STUN 服务器 (比如 stun.l.google.com:19302)
    "我出去后的地址是什么？"
    <── 回复: 100.64.0.2:54321
```

### 3.2 手动测试 STUN

```bash
# 很多语言都有 STUN 库，命令行可用 curl 到一些公开服务做简单探测
# 更直观的方式：运行 WebRTC 测试页或 tailscale netcheck
tailscale netcheck
```

`tailscale netcheck` 输出里会显示：

```text
UDP: true
IPv4: yes, 100.64.0.2:54321
Derp: 200ms (Singapore)
```

这就是你的 NAT 类型和 STUN 探测结果。

## 4. 打洞（Hole Punching）

### 4.1 原理

两设备同时向对方的**外部映射地址**发送 UDP 包：

```text
A 外部: 100.64.0.2:54321          B 外部: 100.64.0.3:54321
   A ──────── 往 B 的外部地址发包 ────────► B
   A ◄─────── 往 A 的外部地址发包 ──────── B
```

两个包几乎同时穿过各自的 NAT：

- A 的包到达路由器 B 时，路由器 B 恰好有"刚才 B 发出去"留下的映射，
  于是放行；
- B 的包同理到达 A。

于是双方建立了**直连**，之后不再需要服务器参与。

### 4.2 为什么是 UDP 而不是 TCP

UDP 无连接，一个"凭空到达"的包就能打通映射；TCP 有握手状态，
很多 NAT 会拒绝没有主动发起过的 TCP 入站，打洞成功率低。

这也是很多 P2P 软件（语音、视频、游戏、Tailscale）优先用 UDP 的原因。

---

## 5. 什么时候打洞会失败

| 情况 | 原因 | 结果 |
|------|------|------|
| 对称 NAT | 每次向不同目标发包都分配不同端口，映射不可预测 | 打洞失败 |
| 运营商 CGNAT | 映射由运营商设备管理，你无法控制 | 可能失败 |
| 严格防火墙 | 路由器/防火墙默认丢弃所有入站 UDP | 打洞失败 |
| 设备离线/睡眠 | 映射失效 | 连接中断 |

此时需要 **TURN 中继**。

---

## 6. TURN：中继兜底

### 6.1 TURN 是什么

**TURN（Traversal Using Relays around NAT）** 就是一个公网中继服务器：

```text
A ──加密──> TURN 中继服务器 <──加密── B
              ↑ 数据由服务器转发
```

代价是**延迟更高、消耗服务器带宽**，但**一定连得通**。

### 6.2 典型策略：先直连，不行再中继

现代组网工具的策略：

```text
尝试打洞（UDP 直连） ──失败──> 尝试 TCP 直连 ──失败──> TURN/DERP 中继
```

Tailscale 的中继叫 **DERP**；WebRTC 里的中继就是 TURN；frp 本质上也是
"服务器中继"（第 6 课）。

---

## 7. 工具如何利用这些原理

| 工具 | 打洞 | 中继 | 说明 |
|------|------|------|------|
| Tailscale | 自动 UDP 打洞 | DERP 中继 | 用户无感，`netcheck` 可观察 |
| ZeroTier | 自动打洞 | 自建/官方 root 服务器 | 同上 |
| frp | 不做打洞，服务器直连转发 | 服务器中继 | 简单可靠，需公网服务器 |
| WebRTC | ICE 打洞 | TURN | 浏览器视频/通话、P2P 传输 |
| 游戏联机 | NAT 打洞 | 服务器中转 | 组队系统常用 |

## 8. 动手练习

1. 在已装 Tailscale 的设备上运行 `tailscale netcheck`，记录：
   - UDP 是否可用；
   - 你的外部映射地址；
   - 延迟最低的 DERP 节点。
2. 与同事互ping Tailscale IP，再用 `tailscale status` 看
   是否显示 `direct`（直连）还是 `relay`（中继）：

   ```bash
   tailscale ping 同事的IP
   ```

   输出里会标明走的是直连还是 DERP。
3. 断掉其中一台的 Wi-Fi 换手机热点，再观察连接类型是否变化。
4. （思考题）为什么打洞成功后，把 STUN/TURN 服务器关掉，连接还能继续？
   答：因为数据路径已经绕过服务器，服务器只负责"牵线"。

---

## 9. 小结

| 概念 | 一句话 |
|------|--------|
| NAT 映射 | 内部地址 ↔ 外部地址的临时翻译记录 |
| STUN | 帮你查出"自己的外部地址" |
| 打洞 | 双方同时往对方外部地址发包，建立直连 |
| 对称 NAT/CGNAT | 打洞失败的常见原因 |
| TURN/DERP | 打不通时的公网中继兜底 |

**工具体验 = 打洞优先 + 中继兜底**。作为使用者，你不需要手工打洞，
但理解原理后，你就能看懂 `tailscale netcheck` 的结果，
也知道为什么"有时候直连、有时候走中继"。
